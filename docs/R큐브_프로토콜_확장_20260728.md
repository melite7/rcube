# R큐브 프로토콜 확장 규격 (2026-07-28)

원본 프로토콜 `docs/R큐브_프로토콜_BLE_CAN__20260703.xlsx`를 **보완**하는 확정 규격이다.
xlsx는 OpCode 번호와 이름만 정의하고 페이로드 레이아웃 상당수가 비어 있어, 펌웨어와 앱이
합의해 온 계약을 여기에 못 박는다. 이 문서와 xlsx가 함께 **단일 소스**를 이룬다.

- xlsx를 고칠 때: `python tools/gen_protocol.py` 재실행
- **이 문서의 §1 표를 고칠 때도 같은 명령을 실행한다** — 생성기가 이 표를 함께 파싱한다
- 생성물(`shared-protocol/*.h`, `*.py`)은 손으로 고치지 않는다

정수는 별도 표기가 없으면 **big-endian**, 부호 있는 값은 2의 보수다. 표준 프레임은
`[0]TargetId [1]OpCode [2:3]PacketSize(BE) [4:]payload`이며 PacketSize는 헤더를 포함한
전체 길이다.

---

## 1. 신규 OpCode

<!-- GEN:OPCODES -->

| 이름 | 코드 | 분류 | BLE/CAN |
|---|---|---|---|
| MotionComplete | B7 | CONTROL-Motion | 공통 |

<!-- /GEN:OPCODES -->

`MotionComplete`(0xB7)는 큐브가 스스로 올리는 **비요청 통보**다. 요청-응답이 아니라
`SetMultiroleInAction`(0xA1)과 같은 이벤트 계열이다.

CAN 우선순위는 **`RCUBE_PRI_SAFETY_SYNC`(1)** 로 둔다. 이 통보는 다음 동작 단계를 여는
게이트(기획서 12.9 in-position handshake)라서, 다른 축의 모션 트래픽(우선순위 2) 뒤에
밀리면 유닛 전체가 멎는다. 짝이 되는 트리거 `ExecuteBuffer`(0xC7)도 같은 클래스다.

## 2. 기존 OpCode 페이로드 확정 (현재 구현 반영)

지금까지 펌웨어·앱이 합의해 쓰고 있으나 xlsx에 레이아웃이 없던 것들이다. 실보드로 검증된
항목은 ✅, 코드만 있고 하드웨어 검증 전인 항목은 ⚠️로 표시한다.

### 2.1 CmdAck — `0xAF` ✅

```
payload = [요청 OpCode][ResultCode]
```
ResultCode 0x00 = OK. 그 외는 `rcube_resultcodes.h`.

### 2.2 SetMultiroleAggregator — `0xA0` ✅

```
payload = [ConnectionLinkCount][GroupMode][Flags]
  ConnectionLinkCount : 허브 포함 총 큐브 수 N
  GroupMode           : 0x0A=그룹 무관, 0x1A=같은 그룹만 (필터는 미구현)
  Flags               : 0x00 고정 — 예약
```

**Flags는 더 이상 고정형 여부를 싣지 않는다.** 기획서 7.5 [새 방식]대로 허브 큐브가 자기
저장 노드ID 유무로 스스로 판정한다(노드ID≠0 → 고정형).

### 2.3 SetMultiroleInAction — `0xA1` ✅ (비요청 통보)

```
payload = [현재 연결된 멤버 수]   ※ 허브 자신 제외
```

**알려진 한계**: 멤버 "수"만 실어서 어느 노드ID가 붙었는지 알 수 없다. 고정형에서는 가상ID가
연결 순서가 아니라 광고 노드ID라 상위가 매핑을 추측할 수 없다. → §6 미결 항목.

### 2.4 SetSK6812LED — `0xE0` ✅

```
payload = [n][R,G,B] × n
```
n=0이면 소등. 큐브는 LED0 색을 노드ID LED(코너 2개)에 적용한다.

### 2.5 SetNodeConfig — `0xD3` ✅

`payload[0]`이 서브커맨드다.

| 서브 | payload | 동작 |
|---|---|---|
| `0x01` SET_GROUP | `[0x01, group_id]` | 그룹번호 저장 후 ~800ms 뒤 재부팅 |
| `0x03` SET_NODE | `[0x03, node_id]` | 노드ID 저장 후 재부팅 |
| `0x04` SET_NETCONF | `[0x04, node_id, cmf, term_id]` | 저장만(재부팅 없음). cmf 0=BLE/1=CAN |
| `0x05` REBOOT | `[0x05]` | 재부팅 |

`0x02`(FIX_ORDER)는 **폐기**했다(기획서 7.5 — 노드ID 저장이 곧 고정형이라 별도 전환 명령이
불필요). 값은 재사용하지 않는다.

브로드캐스트(TargetId=0xFF)로 오면 허브가 전 멤버로 먼저 중계한 뒤 자신도 적용한다.

### 2.6 GetNodeConfig — `0xD4` ✅

```
요청 payload = 없음
회신 payload = [group_id, node_id, cmf, term_id]
```

### 2.7 SetEdgeCentralConfig / Get — `0xD5` / `0xD6` ⚠️

```
payload = [ecf, unit_n, term_id, map[8]]        (11바이트)
  ecf     : 1=edge central(리드 큐브), 0=강등(멤버 맵도 삭제)
  unit_n  : 유닛 전체 큐브 수 N (1~8)
  term_id : CAN 세팅 멤버 중 최대 노드ID (자가 종단 판단용)
  map[i]  : 노드ID(i+1)의 통신방식 — 0x00=BLE, 0x01=CAN, 0xFF=유닛에 없음
```
저장만 하고 재부팅하지 않는다. 배선 정리를 위해 이어서 `SetPowerState`를 받는다.
`0xD6`은 같은 레이아웃으로 회신한다.

### 2.8 ResetConfig — `0xD7` ✅

payload 없음. 노드ID=0, CMF=BLE, 종단ID=0, ECF=0, 멤버 맵 삭제 후 재부팅.

### 2.9 SetPowerState — `0xE7` ⚠️

```
payload = [state]     0 = shut down. 그 외 값은 현재 미지원(BAD_PARAM)
```
개발보드에는 전원 차단 회로가 없어 펌웨어가 딥슬립으로 대신하며 BOOT 버튼으로 깨어난다.
메인보드에서는 STM6601 전원 제어로 교체해야 한다.

### 2.10 GetSensors / SetSensorStream — `0xB0` / `0xB1` ⚠️

```
0xB0 요청 payload = 없음
0xB0 회신 payload = [kind][x(int16)][y(int16)][z(int16)]      (7바이트)
  kind 0x00 = 가속도, 단위 mg
  kind 0x01 = 자이로,  단위 0.1°/s

0xB1 payload = [on] 또는 [on, period_ms(BE16)]
  on=1 시작 / 0 중지, period 20~10000 ms (기본 200)
```

**7바이트로 맞춘 이유**: Classic CAN 데이터필드(8B)에 멀티프레임 없이 들어가야 한다.
한 번 보고는 가속도·자이로 2프레임으로 나간다.

`0xB1`이 브로드캐스트로 오면 허브/edge central이 전 멤버로 팬아웃한 뒤 자신도 적용한다 —
허브도 유닛의 한 큐브이므로 자기 센서를 함께 올린다(기획서 9장).

### 2.11 모션 명령 — `0xC0·C1·C8·C9·CB`, `0xD0`, `0xB2·B6` ⚠️

`mode`는 공통으로 `0x00`=Immediate(즉시 실행), `0x01`=Buffered(적재만, `ExecuteBuffer` 대기)다.
아래 레이아웃은 모두 **8바이트 이하**라 CAN 단일 프레임으로 나간다(멀티프레임 불필요).

| Op | 이름 | payload | 길이 |
|---|---|---|---|
| `0xC0` | SetSingleSpeed | `[mode][velocity(int32, 0.01°/s)]` | 5 |
| `0xC1` | SetSingleAngle | `[mode][position(int32, 0.01°)][t_ms(uint16)]` | 7 |
| `0xC8` | MoveToOrigin | `[mode][t_ms(uint16)]` | 3 |
| `0xC9` | SetThisToOrigin | 없음 — 현재 위치를 원점으로 저장 | 0 |
| `0xCB` | SetDriveState | `[state]` | 1 |
| `0xD0` | EmergencyStop | 없음 | 0 |

`SetSingleAngle`의 `t_ms`는 **도달 시간**이다(기획서 11장 "목표위치 + 도달시간"). 0이면
드라이버 기본 속도로 간다. 웨이포인트로 변환할 때 `t_offset_us = t_ms × 1000`이 된다.

`SetDriveState`의 `state`:

| 값 | 의미 |
|---|---|
| `0x00` | Disable — 게이트 차단 + 전류 0 |
| `0x01` | Enable — 게이트 인에이블 |
| `0x02` | QuickStop — 즉시 안전 정지(큐 비움) |
| `0x03` | FaultReset — 차단 후 재인에이블 |

`EmergencyStop`(0xD0)은 CAN 우선순위 최상위(`RCUBE_PRI_ESTOP`)다. 큐를 비우고 게이트를
차단한 뒤 `MotionComplete(reason=0x02)`로 통보한다.

**조회 회신** (요청 payload는 없음):

```
0xB2 GetMotorStatus 회신 = [err_code][position(int32, 0.01°)][current(int16, 0.01A)]   (7B)
0xB6 GetPosition    회신 = [position(int32, 0.01°)]                                    (4B)
```

온도·입력전압은 이 프레임에 넣지 않는다. 8바이트를 넘겨 CAN 멀티프레임이 필요해지고,
주기 관측은 센서 스트림(§2.10)의 몫이기 때문이다. `err_code`는 드라이버 상태코드
원본이며 0이 정상이다.

## 3. 다축 동기 — TimeSync · 버퍼 실행

기획서 12.9 [버퍼 실행 모델]을 와이어 규격으로 확정한다.

### 3.1 왜 ESP32가 해야 하는가

모터 드라이버(CubeMars AK 시리즈)의 UART 규격에는 **예약 실행도 버퍼도 없다.** 명령을
받으면 즉시 실행한다. 따라서 "여러 축이 T0에 일제히 출발"은 각 큐브의 ESP32가 자기 시계로
T0까지 기다렸다가 첫 키프레임을 드라이버에 내려보내는 방식으로만 구현된다.

**T0 동기 정확도 = 큐브 간 시계 동기 정확도**다. TimeSync가 없으면 다축 협조가 성립하지 않는다.

### 3.2 TimeSync — `0xD2`

시각 값은 **48비트 마이크로초(6바이트 BE)**를 쓴다. 64비트로 잡으면 요청이 9바이트가 되어
CAN 단일 프레임(8B)을 넘긴다. 48비트면 ±4.4년이라 부팅 후 상대시각으로는 넉넉하다.

```
요청/배포 payload = [flags][value (48비트, BE)]                    (7바이트)
  flags bit0 (0x01) : 왕복 측정 요청 — 큐브가 회신한다
  flags bit1 (0x02) : value가 절대시각이 아니라 오프셋 보정값(부호 있음)
  flags bit7 (0x80) : 회신 표시(큐브 → 마스터)

회신 payload = [flags|0x80][value 그대로 6B][t_recv 6B][t_send 6B]  (19바이트)
```

**두 단계로 맞춘다.**

1. 마스터가 `flags=0x01`, `value=T1`(자기 시각)로 요청 → 큐브가 `t_recv`(수신 시 로컬),
   `t_send`(회신 시 로컬)를 실어 회신. 마스터는 도착 시각 `T4`를 찍는다.
2. 마스터가 SNTP 식으로 계산한다.
   ```
   theta  = ((t_recv - T1) + (t_send - T4)) / 2     // 큐브로컬 - 마스터
   offset = -theta                                  // 마스터 = 로컬 + offset
   RTT    = (T4 - T1) - (t_send - t_recv)
   ```
   그런 뒤 `flags=0x02`, `value=offset`으로 보내 큐브에 적용시킨다.

`flags`가 `0x00`이면 큐브가 `offset = value - 로컬시각`으로 즉시 맞춘다(단방향). 편도 지연만큼
오차가 남으므로 정밀도가 필요 없을 때만 쓴다.

- **기준 시계**: 각 큐브의 `esp_timer_get_time()`(부팅 후 마이크로초). 절대 시각이 아니다.
- **재동기 주기**: BLE 5초, CAN 30초 권장. 기획서 11장 [클럭 드리프트] 대응.
- **RTT가 여러 번 측정되면 최솟값을 쓴다** — BLE는 connection event 대기로 지터가 큰데,
  최소 RTT 표본이 편도 지연에 가장 가깝다.
- **CAN**: 요청·배포(7B)는 단일 프레임으로 나가지만 회신(19B)은 §5 멀티프레임이 필요하다.
  CAN은 지연이 결정적이라 단방향 배포만으로도 충분하므로, 왕복 측정은 BLE에서만 쓴다.

### 3.3 SetScheduledAngles — `0xC2` (궤적 적재)

```
payload = [mode][seq_base(BE16)][count][웨이포인트 × count]

웨이포인트 (12바이트, 전송계층 무관 — 기획서 12.9)
  [0:3] t_offset_us (uint32, BE)  T0 기준 도달 시각
  [4:7] position    (int32,  BE)  0.01° 단위
  [8:9] velocity    (int16,  BE)  0.01°/s 단위, 0=드라이버 자동
  [10]  flags       bit0=in-position 확인 지점(도달 시 MotionComplete 통보)
  [11]  reserved    0
```

`mode`: `0x00`=Immediate(받는 즉시 실행), `0x01`=Buffered(적재만).

`seq_base`는 이 묶음의 첫 웨이포인트 순번이다. 분할 전송 시 누락·중복을 상위가 판정한다.

### 3.4 ExecuteBuffer — `0xC7` (실행 트리거)

```
payload = [action][t_start_us (uint64, BE)]       (9바이트)
  action 0x01 = Run    : t_start_us(마스터 시계 기준)에 출발
         0x02 = Cancel : 실행 중이면 안전 감속 후 정지
         0x03 = Flush  : 미실행 버퍼 폐기
```

`Run`인데 버퍼가 비어 있으면 `RCUBE_RC_*` NAK으로 거부한다(기획서 12.9).
`t_start_us=0`이면 즉시 출발.

**브로드캐스트 Run이 다축 동기의 핵심이다.** edge central이 각 축에 궤적을 Buffered로
적재한 뒤 `Run(T0)`을 브로드캐스트하면 전 축이 T0에 일제히 출발한다. BLE 지터는 적재
단계에서 흡수되고, 출발 시점만 T0가 맞춘다.

## 4. MotionComplete — `0xB7` (도달 완료 통보)

```
payload = [reason][seq(BE16)][position(int32, BE)][err_code]     (8바이트)
  reason 0x00 = in-position 도달(웨이포인트 flags bit0 지점)
         0x01 = 버퍼 전체 실행 완료
         0x02 = Cancel로 중단됨
         0x03 = 폴트로 중단됨(err_code 참조)
  seq       : 완료된 웨이포인트 순번
  position  : 완료 시점 실제 위치, 0.01°
  err_code  : reason=0x03일 때 드라이버 에러코드, 그 외 0
```

8바이트라 CAN 단일 프레임으로 나간다.

이 통보가 있어야 미션코드의 `wait_done()`이 폴링 없이 성립한다. 없으면 상위가
`GetMotorStatus`를 주기적으로 긁어야 해서 링크 부하와 지연이 함께 커진다.

## 5. CAN 멀티프레임 (MULTI 비트)

CAN 29비트 ID의 `MULTI`(bit 17)는 xlsx에 자리만 있고 사용 규격이 없었다. 확정한다.

`MULTI=0`이면 단일 프레임(지금까지의 모든 명령). `MULTI=1`이면 분할 전송이며,
**데이터필드 첫 바이트가 세그먼트 헤더**이고 나머지 7바이트가 페이로드 조각이다.

```
세그먼트 헤더 (1바이트)
  bit7    : 1=첫 세그먼트(FIRST)
  bit6    : 1=마지막 세그먼트(LAST)
  bit5:0  : 세그먼트 순번 0~63 (첫 세그먼트는 0)
```

- 첫 세그먼트(FIRST=1)의 페이로드 처음 2바이트는 **전체 페이로드 길이(BE16)**이고, 그
  뒤부터 실제 데이터가 시작된다 → 첫 세그먼트 데이터 5바이트, 이후 7바이트씩.
- 최대 길이 = 5 + 63×7 = **446바이트**. `SetScheduledAngles`(§3.3)로 환산하면 헤더
  4바이트를 뺀 442바이트, 즉 웨이포인트(12B) **36개**가 한 묶음의 상한이다
  (`4 + 36×12 = 436` ≤ 446). 더 필요하면 `seq_base`를 올려 여러 묶음으로 나눈다.
- 수신 측은 `(SrcId, OpCode)`별로 재조립 버퍼를 하나 둔다. 순번이 어긋나거나
  **200ms 안에 LAST가 오지 않으면 버리고** 재조립을 포기한다(부분 실행 금지).
- FIRST 없이 중간 세그먼트가 먼저 오면 버린다.

BLE는 MTU가 충분하므로 이 분할을 쓰지 않는다. **같은 명령이 CAN에서는 분할되고 BLE에서는
단일로 나가되, 재조립 후의 페이로드는 완전히 동일하다** — 상위 레이어는 차이를 모른다
(기획서 12.9 [전송계층 무관 웨이포인트 포맷]).

## 6. 미결 항목

확정하지 않고 남긴 것들이다. 구현 전에 결정해야 한다.

1. **`0xA1`에 가상ID 목록 부재** — 멤버 수만 실어서 고정형에서 어느 노드가 붙었는지 모른다.
   페이로드를 `[count][node_id × count]`로 확장하는 안이 유력하나, 기존 앱과의 호환을
   깨므로 별도 결정이 필요하다.
2. **ERPM ↔ 축 각속도 환산** — 드라이버는 전기적 회전수(ERPM)를 쓴다. 극쌍수와 감속비가
   있어야 §3.3의 `velocity`(0.01°/s)를 ERPM으로 바꿀 수 있다.
3. ~~모터 UART 보레이트~~ → **921600으로 확정(2026-07-28).**
4. **`GetMotorStatus`(0xB2) 페이로드** — 드라이버 `GET_VALUES`(0x45) 회신에 온도·출력전류·
   입력전압·에러코드·엔코더각이 모두 있다. 그중 무엇을 올릴지, 센서 스트림(§2.10)에
   합칠지 결정 필요.
5. **그룹번호 필터링** — `GroupMode=0x1A`(같은 그룹만 연결)를 허브가 무시하고 있다.

## 부록. 모터 드라이버 UART 규격 요약 (참고)

각 큐브 ESP32 ↔ 모터보드 구간은 **R큐브 프로토콜이 아니라 CubeMars AK 시리즈 규격**이다
(`docs/모터제어명령규격.pdf` 4.3.2). 계층이 다르므로 혼동하지 않는다.

```
[0xAA][LEN][ID][data…][CRC hi][CRC lo][0xBB]
  LEN = ID+data 길이 (헤더·CRC·테일 제외)
  CRC = CRC-16/XMODEM (poly 0x1021, init 0x0000), 대상 = ID+data
```

| ID | 명령 | 스케일 |
|---|---|---|
| `0x46` SET_DUTY | duty | ×100,000 |
| `0x47` SET_CURRENT | A | ×1,000 |
| `0x49` SET_RPM | ERPM | ×1 |
| `0x4A` SET_POS | 도(°) | **×1,000,000** |
| `0x3C` SET_POS_SPD | 도, ERPM, 가속 | **pos ×1,000**, 나머지 ×1 |
| `0x60` MIT | pos·spd·cur·kp·kd | 각 ×1,000 |
| `0x45` GET_VALUES | — | 상태 1회 회신 |
| `0x4C` SET_DETECT | — | 위치 10ms 주기 피드백 |

⚠️ **`SET_POS`는 ×1,000,000, `SET_POS_SPD`는 ×1,000으로 스케일이 1000배 다르다.**
벤더 문서 4.3.2.2의 5번과 7번이 실제로 그렇게 정의돼 있다. 드라이버 레이어에서 명령별
상수로 분리한다.

위 표는 매뉴얼의 예제 프레임 13개로 CRC와 스케일을 전수 검증했다(2026-07-28).
