0. R큐브 하드웨어 구성
================================================================================
[R큐브 구성]
  - 정육면체 케이스 내부에 메인보드와 QDD모터(제어보드 포함) 탑재됨
  - R큐브 외형은 10cm x 10cm x 10cm 정육면체
  - R큐브는 모터면을 제외한 5개 면에 표식장치(숫자, 기호)를 가짐.
  - R큐브는 모든 6면(모터면 포함)에 외부링크를 연결하는 나사/홀 규격이 동일함 (나사 4개 + 홀 4개)
  - 모터면 제외한 5면은 중앙부는 조립부영역은 알루미늄합금이고 나머지 모서리부분은 엔지니어링 플라스틱으로구성

[R큐브 면구분]
  - 모터 회전면이 1번면
  - 모터 회전면의 윗면(모터의 절대원점이 향하는쪽)이 2번면
  - 위 2번부터 시계방향으로 3, 4, 5번면
  - 모터 회전면 뒷면이 6번면
  * 전원버튼, 입출력단자는 2,3번면이 만나는 모서리와 4,5번면이 만나는 모서리에 위치함

[R큐브 사용 용도]
  - R큐브는 QDD 모터를 내장하고 있고 BLE/CAN 로 연결하여 사용하는 준산업용 로봇모듈
  - R큐브와 외부 표준링크들을 연결하여 로봇을 만들고 큐브끼리 통신으로 연결하여 로봇을 만듬
  - 중앙제어장치(컴퓨터 등)에 R큐브들을 연결하여 하여 로봇을 동작할 수 있음
  - 대표 R큐브를 선정하면 R큐브들끼리 모여 저장된 미션을 수행할 수 있음
  - 메인보드의 외부커넥터를 통해 CAN통신, RC서모보터제어, 외장센서연결 등을 할 수 있음.

[메인보드]
  - ESP32-S3-WROOM-1-N16R2
  - CAN 트랜시버 (TJA1042T/3)
  - IMU (BMI088)
  - CAN 종단저항회로 탑재
  - 칼라 LED (WS2812B-B-V6) 3개 (2개는 노드ID 등을 보여주는 코너 LED로 사용, 1개는 그룹번호를 보여주는 LED로 활용)
  - 버튼입력: 택트스위치 + STM6601
  - 부저 (CMT-1032-85-SMT-TR)
  - POWER IN : XT60PW-M (48V, GND)
  - CAN IN: 2핀 (B02B-PASK-2) - CAN연결용 (CAN-H, CAN-L)
  - CAN OUT: 2핀 (B02B-PASK-2) - CAN연결용 (CAN-H, CAN-L)
  - SENSOR : 4핀(B04B-PASK-2) - 외부센서용 (GND, 5V, IO1, IO2)
  - SERVO : 3핀(Molex 5268-03A) - RC서보모터용 (SIG, 12V, GND)
  - USB-C : Ctype 프로그래밍용
  - SPI카메라 : JST GH1.25 6핀 SPI
  - 메인보드-모터제어보드 연결 커넥터
    * 8핀 (GND / TX / RX / FAULT / GATE_EN/ BOOT0 / nRST / RESERVED )
    * 2핀 모터제어보드로 48V, GND를 입력해주어야 함.

[QDD 모터 모듈]
  - 제어보드(STM32G4계열 CPU사용) 포함된 일체형 모듈
  - 외전형 BLDC 유성기어 및 엔코더 2개 내장.
  - 메인보드 CPU와 UART로 연결
  - ★제어 분담: 메인보드 ESP32는 20~50Hz로 키프레임(목표위치+도달시간/속도)만 내려
    보내고, 모터제어보드(STM32G4-)가 1kHz 이상 서보 루프로 실시간 제어·보간을 전담한다.
    (상세 11장 / 12.9)

1. 핵심 개념 및 용어 정의
================================================================================

[역할 용어]
  - R큐브
      로봇을 구성하는 기본 모듈. 내부에 감속기모터와 제어/통신 보드를 갖춘
      정육면체 단위. 1개~N개를 연결해 로봇을 만든다.

  - 로봇유닛
      특정목적을 달성하기 위해 R큐브들과 로봇링크들이 연결되어 만들어진 시스템.
      독립로봇유닛 또는 서브로봇유닛으로 구성된다. R큐브끼리는 BLE 또는 CAN으로
      통신을 주고받으며, ★통신방식은 큐브마다 개별 지정할 수 있어 한 유닛 안에서
      CAN 큐브와 BLE 큐브가 혼합될 수 있다.

  - edge central 큐브
      독립로봇유닛에서 나머지 R큐브들을 제어·모니터링하고, 자신에 저장된
      미션코드를 실행하는 중심 큐브. 항상 노드 01(=리드 큐브)이다.
      ※ 독립로봇유닛으로 전환 시 PC로부터 "멤버큐브별 {노드ID, CMF} 맵"을 함께 받아 저장한다(7.3).
        부팅 시 이 맵을 보고 필요한 통신 서버만 켜고(CAN 멤버가 있으면 CAN 서버
        =TWAI, BLE 멤버가 있으면 BLE 서버=NimBLE, 둘 다면 둘 다), 노드ID 순서대로
        각 멤버의 통신방식에 맞게 연결한다. ESP32-S3는 BLE와 TWAI가 독립 페리페럴
        이므로 동시 운용이 가능하다. (12장 참조)
      ※ 유닛에 CAN 멤버가 있으면 edge central은 자기 CMF와 무관하게 CAN 버스에 올라가
        컨트롤러로 동작하며, 자신의 CAN 버스의 한쪽 끝을 종단한다. (13장)
      ※ 독립로봇유닛에서 BLE 멤버큐브는 BLE 허브 큐브를 거치지 않고 edge central이 직접
        BLE로 연결한다(NimBLE central 다중 연결).

  - 리드 큐브 (Lead Cube)
      노드 01 큐브를 가리킨다. 서브로봇유닛에서 독립로봇유닛으로 전환할 때 미션
      코드가 업로드되고 edge central 역할을 맡게 되는, 유닛에서 가장 중요한 큐브다.
      통신방식(CAN/BLE)과 무관하게 "연결 순서상 첫 번째(노드 01)"라는 의미를 갖는다.
      ※ 서브로봇유닛 단계에서는 아직 edge central이 아니라 일반 멤버로 동작한다.
        다만 독립 전환 시 미션코드 + 멤버 맵 업로드 대상이자 edge central이 될 큐브이다.

  - BLE 허브 큐브 (BLE Hub Cube)   ★서브로봇유닛 전용
      서브로봇유닛에서, BLE로 세팅된 큐브들 중 노드ID가 가장 작은 큐브. PC에 BLE로
      가장 먼저 연결되며, multirole(peripheral+central)로 동작해 나머지 BLE 세팅 멤버
      큐브들을 연결한다. BLE 세팅 멤버들의 센서값을 취합해 PC로 올리고, PC 명령을 BLE
      멤버들에게 분배한다.
      ※ CAN으로 세팅된 큐브는 PC(USB-CAN)에 직접 붙으므로 BLE 허브 큐브를 거치지
        않는다. BLE 허브 큐브는 "서브로봇유닛의 BLE 분기"만 담당한다.
      ※ 순수 BLE 서브로봇유닛(모든 큐브가 BLE)에서는 리드 큐브(노드01)와 BLE 허브 큐브가
        동일한 큐브이다. 혼합 서브로봇유닛에서 노드 01이 CAN으로 세팅되면, BLE 허브 큐브는
        BLE 세팅 큐브 중 최소 노드ID(예: 노드 03)인 다른 큐브가 된다.
      ※ 독립로봇유닛에는 BLE 허브 큐브가 없다. edge central(노드01)이 모든 BLE 멤버를
        직접 연결한다. (3장, 5장, 7.4)

  - 멤버 큐브
      리드 큐브/edge central/BLE 허브 같은 특수 역할을 제외한 일반 R큐브. 자신의
      CMF에 따라 CAN 또는 BLE로 상위에 붙는다.
        · 서브 : CAN 멤버는 PC(USB-CAN) 직접, BLE 멤버는 BLE 허브 경유.
        · 독립 : CAN 멤버는 edge central(CAN) 직접, BLE 멤버는 edge central(BLE) 직접.

[저장 설정 플래그] (R큐브 플래시에 저장)
  - ECF (Edge Central Flag)        : 0 = 일반,        1 = edge central 모드
  - CMF (Communication Mode Flag)  : 0 = BLE,         1 = CAN
        ★ 큐브별 통신방식 저장 플래그. 한 유닛 안에서 큐브마다 값이 다를 수 있다.
        ★ 공장 출하 기본값 = 0 (BLE). PC의 통신방식 세팅 화면에서 큐브별로 0/1을 저장한다.
  ※ 연결 순서 방식(고정형/비고정형)은 별도 플래그로 저장하지 않고, 노드ID 할당
     여부로 판정한다: 노드ID=0x00(미할당) -> 비고정형(초기 구성 단계),
     노드ID=1~8 -> 고정형. 통신방식 세팅 화면에서 노드ID/CMF를 저장하는 순간 곧
     고정형이며, 별도의 "고정형 전환 명령"은 없다. (7.5 참조)
  ※ edge central(ECF=1) 큐브는 위 자기 플래그에 더해 "멤버별 {노드ID, CMF} 맵 +
     전체 큐브 수 N + 종단노드ID"를 추가로 저장한다(7.3, 12.6).
  ※ CMF=1(CAN) 큐브는 부팅 시 자가 종단 판단을 위해 "종단노드ID"(= 그 유닛에서 CAN으로
     세팅된 큐브 중 최대 노드ID)도 자기 플래시에 저장한다. 이 값은 통신방식 세팅 저장 단계
     (7.2/7.3)에서 PC가 기록한다. (13장)
  ※ 위 저장 값(ECF/CMF/노드ID) 및 멤버 맵은 설정 모드에서 외부(PC/앱)가 재설정·
     초기화할 수 있다. (5장 [설정 모드] 참조)

[식별자]
  - 그룹번호 (GG)
      다수의 로봇유닛이 함께 존재할 때, 같은 로봇유닛을 구성하는 R큐브들끼리만
      BLE로 연결되도록 부여하는 가상의 번호. (출하 기본값 0)
      ※ 그룹번호는 다수의 로봇유닛이 있을 경우 서로 블루투스를 사용할 경우 BLE혼선방지를 위해 각각의 로봇유닛들에게 그룹번호를 주어
         해당 로봇유닛 안에 있는 큐브들끼리만 서로 연결되도록 하는 기능이다.
      ※ CAN으로 세팅된 큐브는 버스가 물리적으로 분리되므로 그룹번호가 의미가 없다.

  - 노드ID (NN)
      각 큐브의 연결 순서를 정하는 식별자. 유닛 전체에서 유일하며, 통신방식이
      혼합이어도 노드ID는 1부터 연속으로 부여한다(역할 순서 = 노드ID 순서).
        · CAN 통신: 메시지ID + 노드ID 사용해서 구분
        · BLE 통신: 장치이름 + 노드ID 사용해서 구분
      로봇유닛 구성시 1~8만 사용가능, 안정적 사용 위해 5 이하 사용 권장.
      (출하 기본값 0x00 = 미할당)

  - 노드ID의 두 종류 (저장 / 가상)   ★
      · 저장 노드ID (고정형) : 플래시에 저장된 1~8. 큐브가 부팅부터 자기 ID를 알고 그
        색으로 점멸(연결 전)/점등(연결 후)한다.
      · 가상 노드ID (비고정형) : 저장 노드ID가 없을 때(0x00), PC(또는 BLE 허브)에 연결
        되는 "순서"로 상위가 실시간 배정하는 임시 ID(1..N). 저장하지 않는다. 큐브는 연결
        전 흰색 점멸하다가, 연결되어 가상 노드ID가 배정되면 그 색으로 점등한다.

  - 색상 (RGBCMYVO)
      노드ID(저장 또는 가상)에 따라 부여되는 색상. R큐브 코너 칼라 LED로 표시된다.
        0:흰색(White, 미할당)  1:Red  2:Green  3:Blue  4:Cyan  5:Magenta  6:Yellow  7:Violet  8:Orange  9:연한 Red(Light Red)
      · 비고정형(노드ID 미할당) : 연결 전엔 흰색으로 1Hz 점멸하다가, PC/허브에 연결되어
        가상 노드ID가 배정되면 그 가상 노드ID 색으로 점등한다. ★PC에 처음 연결된 큐브는
        가상 노드ID 1이 되어 Red로 켜지며 멀티롤(BLE 허브)을 시작하고, 다음 큐브는 가상2=
        Green, 그 다음 가상3=Blue … 순으로 점등한다.
      · 고정형(노드ID 1~8 저장) : 연결 전엔 저장 노드ID 색으로 1Hz 점멸하다가, 연결이
        완료되면 그 색으로 상시 점등한다. 리드/edge central(노드01)은 Red이다. (혼합에서
        노드01이 CAN이고 BLE 허브가 노드03이면 그 허브는 Blue로 켜진다.)

[로봇유닛 표기]
  - 유닛에 포함된 R큐브 개수에 따라 R1, R2, R3 ... 모델 로 표기한다.
  - 한 로봇유닛에 연결 가능한 최대 큐브 수는 8개(R8)이다.
  - BLE/CAN 통신 안정성을 고려하여 실제 사용은 R5 이내를 권장한다.

================================================================================
2. 하드웨어 구성
================================================================================

[전체구조]
  - 내부에 QDD모터(=감속기모터+모터제어기보드)와 QDD모터를 제어하고 큐브간 통신을 담당하는 메인보드가 들어있다.
  - 정육면체 구조이며, 1면은 모터 회전면, 나머지 5면은 외부 링크 고정면이다.
  - R큐브의 크기는 한 변의 길이가 100mm 인 정육면체이다.

[모터제어보드 - STM32G4-]
  - 감속기모터에 부착된 모터제어보드에는 STM32G4-가 CPU가 되고 2개의 엔코더IC
    및 제어관련 IC가 탑재된다.
  - 모터제어보드는 메인보드로부터 UART 통신으로 명령을 받아 모터 제어만을 전담한다.
  - ★실시간 서보 제어 전담: 엔코더 기반 위치/속도/토크 제어 루프를 1kHz 이상(예:
    1~10kHz)으로 돌리며, 메인보드(ESP32)가 20~50Hz로 내려보낸 키프레임(목표위치+
    도달시간/속도) 사이를 스스로 보간해 매끄러운 모션을 만든다. 즉 "실시간 제어"는
    전적으로 STM32G4-의 몫이다. (상세 11장 / 12.9)

[메인보드 - ESP32-S3]
  - 메인보드에는 ESP32-S3 CPU를 사용한다.
  - 역할: BLE/CAN 통신, 저장된 프로그램 수행, edge central일 때 다른 R큐브
    제어·모니터링.
  - ESP32는 모터제어보드 STM32G4-에 UART로 모터 제어값(위치/속도/토크 등)만
    전송하고, 실제 모터 구동은 STM32G4-가 담당한다.
  - ★ESP32는 실시간 서보 루프를 직접 돌리지 않는다. 20~50Hz 주기로 "키프레임(목표
    위치 + 도달시간 또는 목표속도)"만 생성·전송하는 키프레임 생성기/감독자 역할이며,
    1kHz 이상 실시간 제어·보간은 STM32G4-가 전담한다. (11장 / 12.9)
  - ESP32에서는 현재 모터의 각도, 속도, 명령수행현황, 오류현황 등을 STM32G4-로
    부터 주기적으로 받아온다.
  - STM32G4-에서는 일정시간 ESP32로부터 명령신호를 받지 못하면 스스로 정지한다.
  - 메인보드에는 IMU 센서, 부저 회로, 칼라 LED 제어회로가 포함되며
    모두 ESP32가 제어한다.

[외부확장포트 (범용 4핀)]
  - R큐브 메인보드에는 외부 센서/기기를 붙일 수 있는 범용 4핀 확장포트가 있다.
    핀 구성: 5V / Dout / Ain / GND.
       · 5V, GND   : 외부 장치 전원 공급.
       · Dout, Ain : 2개의 신호핀. 동작 모드에 따라 다목적으로 쓰인다 —
                     I2C(SDA/SCL), UART(TX/RX), 디지털 출력(Dout), 아날로그 입력(Ain).
  - ESP32가 이 포트를 제어하며, 어떤 모드로 쓸지는 전원이 켜질 때 자동 탐지 절차로
    결정한다(아래).

  [전원 ON 시 외부확장포트 자동 탐지 순서]
    R큐브가 처음 전원이 켜지면 다음 순서로 확장포트에 연결된 장치를 탐지하고 초기화한다.
    먼저 발견된 한 가지로 모드가 확정된다 (우선순위: I2C -> UART -> Analog).

    1) I2C 센서 탐지 (최우선)
       - R큐브가 이미 라이브러리를 보유한 I2C 센서들의 I2C 주소를 스캔해, 해당 센서가
         실제로 꽂혀 있는지 확인한다.
       - 꽂혀 있는 것이 확인되면 그 센서(기기)를 I2C 모드로 초기화한다. (탐지 종료)
    2) UART 장치 탐지 (I2C 센서가 없을 때)
       - I2C 센서가 발견되지 않으면, R큐브가 이미 통신 규칙(프로토콜)을 알고 있는 UART
         장치들이 꽂혀 있는지, 정해진 UART 통신 규칙에 따라 확인한다.
       - 확인되면 그 장치(기기)를 UART 모드로 초기화한다. (탐지 종료)
    3) 아날로그 입력 가정 (I2C·UART 모두 없을 때)
       - I2C·UART 장치가 모두 발견되지 않으면, 디지털 장치는 꽂혀 있지 않다고 보고
         Ain 핀에 아날로그 센서가 연결되어 입력 중이라고 가정한다.
       - 이후 Ain 핀의 아날로그 값을 읽는다(ADC).

  ※ 위 탐지·초기화는 12.6 부팅 시퀀스의 공통 초기화 단계에서 수행한다(역할/통신방식과
     무관하게 모든 큐브 공통).
  ※ 확장포트로 읽은 외부 센서 값은 큐브의 일반 센서 데이터와 함께 상위(edge central/PC)
     로 리포팅하거나 미션코드에서 활용할 수 있다(9장, 12.4).

[통신]
  - ESP32 CPU는 자신의 CMF에 따라 BLE 또는 CAN으로 R큐브 간 통신하거나 PC 제어
    프로그램에 연결되어 동작한다. ★통신방식은 큐브별 CMF로 결정되므로, 한 유닛 안에
    CAN 큐브와 BLE 큐브가 혼합될 수 있다.
  - 혼합 유닛에서 상위 제어자는 두 갈래를 동시에 다룬다.
       · 서브로봇유닛: PC가 USB-CAN 어댑터로 CAN 큐브를 직접 제어하고, BLE 허브
         큐브에 BLE큐브들을 붙여 제어한다.
       · 독립로봇유닛: edge central(노드01)이 CAN 멤버는 CAN(TWAI)으로, BLE 멤버는
         BLE(NimBLE central 직접 연결)로 동시에 제어한다. (BLE 허브 없음)
  - CAN을 사용하는 서브로봇유닛에서는 PC측이 USB-CAN 어댑터로 유닛의 CAN 버스에
    직접 접속한다. PC 1대에 여러 USB-CAN 어댑터(또는 다채널 USB-CAN 장치 1대)를
    두면, 어댑터(채널)마다 하나의 서브로봇유닛을 붙여 다중 유닛 공정을 구성할 수
    있다. (3장)

[CAN 종단저항 회로]
  - 모든 R큐브 메인보드에 120Ω 종단저항 + 소프트웨어 제어 스위치(MOSFET/아날로그
    스위치 등)를 둔다. ESP32가 GPIO로 이 스위치를 켜고 끈다.
       · 스위치 OFF : 120Ω이 버스에서 분리됨 (가운데 큐브, 기본 상태).
       · 스위치 ON  : 120Ω이 CAN_H-CAN_L 사이에 연결됨 (CAN 버스 종단 큐브).
  - R큐브 간 링크 커넥터에는 CAN_H/CAN_L 라인이 포함된다.
  - 종단은 CAN으로 세팅된 큐브들이 이루는 CAN 버스에 대해서만 의미가 있다. CAN
    버스의 물리적 양 끝에 놓인 노드만 종단을 켠다. (상세 규칙은 13장 참조)

================================================================================
3. 네트워크(로봇유닛) 구성 모드
================================================================================

R큐브들이 모여 네트워크를 구성할 때는 다음 2가지 모드가 있다. 어느 모드든 각
R큐브의 통신방식(CAN/BLE)은 큐브별 CMF로 개별 지정되며 혼합될 수 있다.

[독립로봇유닛]
  - R큐브 중 노드 01(=리드 큐브)이 edge central 역할을 맡는다.
  - edge central이 나머지 R큐브를 제어하고, 자신에 저장된 미션코드를 실행하여
    주어진 미션을 수행한다.
  - 혼합 통신: edge central은 저장된 멤버 맵에 따라 필요한 통신 서버만 켜고(CAN 멤버만
    있으면 CAN 서버=TWAI만, BLE 멤버만 있으면 BLE 서버=NimBLE만, 둘 다면 둘 다),
    CAN 멤버는 CAN으로, BLE 멤버는 BLE로 노드ID 순서대로 연결·제어한다.
  - ★BLE 멤버는 BLE 허브 큐브를 거치지 않고 edge central이 직접 BLE로 연결한다
    (NimBLE central 다중 연결). 독립로봇유닛에는 BLE 허브 큐브가 없다.
  - 연결 순서는 고정형으로만 동작한다(노드ID 순).

[서브로봇유닛]
  - 모든 R큐브가 PC 제어에 따라 동작한다. 단, 통신방식별로 연결 경로가 다르다.
       · CAN 세팅 큐브 : PC가 USB-CAN 어댑터로 CAN 버스에 직접 올라가 노드ID 순으로
         직접 제어·취합한다(중계 큐브 없음).
       · BLE 세팅 큐브 : PC가 BLE 허브 큐브(BLE 세팅 큐브 중 최소 노드ID)에 BLE로
         붙고, BLE 허브 큐브가 나머지 BLE 멤버를 multirole로 연결해 센서를 취합하고
         명령을 분배한다.
  - 즉 서브로봇유닛의 취합·제어 주체는 PC이며, BLE 분기에 한해 BLE 허브 큐브가
    중간 취합자 역할을 한다.

[서브->독립로봇유닛 전환]
  - 서브로봇유닛으로 사용하다가, 리드 큐브(노드 01)에 미션코드 + 멤버큐브별 통신맵을 업로드하면
    독립로봇유닛으로 전환할 수 있다.
  - 유닛모드 전환 시 각 R큐브는 현재의 연결 순서값을 노드ID로, 통신방식을 CMF로
    이미 저장하고 있어야 한다(7.2/7.3에서 저장됨).

[연결 순서 방식 - 고정형 vs 비고정형]   (상세 흐름은 7.5)
  - 비고정형
      사용자가 큐브들의 순서를 정해, 그 순서대로 하나씩 전원을 켜서 연결하는 방식.
      연결 순서에 따라 상위가 가상 노드ID(1..N)를 배정하고 각 큐브가 그 색으로 점등한다
      (첫 큐브=가상1=Red=멀티롤 허브). 가상 노드ID는 저장하지 않는다.
      ★BLE에서만 가능하며 "통신방식 세팅 전 초기 구성 단계"로만 쓰인다(노드ID 미할당 상태).
  ※ 두 연결 옵션: (A) 사용자 지정 순서(비고정형, 위) / (B) 저장 노드ID 순서 자동(고정형,
     아래). 고정형은 큐브가 광고에 저장 노드ID를 실어, PC/edge central이 켜는 순서와
     무관하게 노드ID 순으로 자동 연결한다.
  - 고정형
      각 R큐브가 노드ID와 CMF를 플래시에 저장해, 그 값에 따라 자동 연결되는 방식.
      ★통신방식 세팅 화면에서 저장을 누르는 순간 노드ID와 CMF가 함께 저장되어
      자동으로 고정형이 된다.

[연결 가능한 로봇유닛 방식]
  - 서브로봇유닛  비고정형  BLE        * 초기 구성(통신방식 세팅 전) 단계 전용
  - 서브로봇유닛  고정형    BLE/CAN 혼합 * 통신방식 세팅 후 정상 운용 형태
  - 독립로봇유닛  고정형    BLE/CAN 혼합

[취합·제어 주체 요약]
  구성        취합·제어 주체   CAN 분기            BLE 분기            종단 ON 위치(CAN)
  ----------------------------------------------------------------------------------
  서브(혼합)  PC               PC가 USB-CAN 직접     BLE 허브 큐브 경유  PC어댑터 + 종단노드ID
  독립(혼합)  edge central     edge central가 CAN     edge central가 BLE  edge central + 종단노드ID
                              직접                   직접 (허브 없음)
  (서브 순수BLE / 독립 순수BLE : CAN 분기 없음 -> 종단 불필요, 전부 OFF)
  (서브 순수CAN / 독립 순수CAN : BLE 분기 없음)

  - 핵심 1: CAN 큐브는 항상 상위(PC 또는 edge central)에 직접 붙는다(중계 없음).
  - 핵심 2: 서브에서는 BLE 큐브가 BLE 허브 큐브를 통해 PC에 묶이고, ★독립에서는
    edge central이 BLE 멤버를 직접 연결한다(허브 없음).
  - 핵심 3: edge central이 필요한지는 "PC가 그 유닛 위에 직접 올라가 있는가"로
    갈린다. 서브는 PC가 직접(USB-CAN/BLE) 제어하므로 edge central이 없고, 독립은
    edge central(노드01)이 PC 역할을 대신한다.

[다중 서브로봇유닛 공정 시스템 (PC + 다중 USB-CAN)]
  - PC 1대에 USB-CAN 어댑터를 여러 개(또는 다채널 USB-CAN 장치 1대) 연결하면,
    어댑터(채널)마다 독립된 CAN 버스 = 하나의 서브로봇유닛의 CAN 분기를 붙일 수
    있다. 각 유닛은 내부적으로 CAN/BLE 혼합일 수 있다.
  - 장점
       · 유닛마다 1Mbps CAN 버스를 전용 -> 유닛 간 대역폭 경쟁 없음.
       · 버스가 물리적으로 분리되므로 CAN 큐브의 노드ID를 유닛마다 재사용 가능.
       · 한 유닛 버스의 장애가 다른 유닛으로 전파되지 않는다(전기적 격리).
  - PC 제어 프로그램은 "채널(어댑터) <-> 유닛" 매핑과 "유닛별 큐브의 노드ID/CMF
    매핑"을 관리하며, 각 유닛의 CAN 분기를 직접, BLE 분기를 BLE 허브 큐브 경유로
    제어·취합하고, 필요 시 라인 전체 정지(E-stop)를 조율한다.
  - 종단은 유닛(버스)마다 독립적으로 맞춘다: 각 CAN 버스에서 PC 어댑터(한쪽 끝) +
    종단노드ID 큐브(반대쪽 끝)만 종단 ON. (13장)

================================================================================
4. R큐브 식별 체계 (그룹번호 / 노드ID / 색상)
================================================================================

  - 색상은 노드ID(저장 또는 가상)에 따라 RGBCMYVO 순으로 부여되고 R큐브 코너 LED에
    표시된다.
  - ★고정형: 각 큐브가 자신의 저장 노드ID 색으로 점등한다(노드01=Red, 02=Green,
    03=Blue … 08=Orange).
  - ★비고정형(초기 구성): 큐브는 저장 노드ID가 없어 연결 전 흰색 점멸하다가, PC에
    연결되는 순서로 가상 노드ID(1..N)를 배정받아 그 색으로 점등한다. PC에 처음 연결된
    큐브는 가상1=Red가 되어 멀티롤(BLE 허브)을 시작하고, 이후 가상2=Green, 가상3=Blue …
    순으로 켜진다(사용자가 큐브 켜는 순서로 가상 노드ID=색이 정해진다).
  - 전체 큐브 수는 사용자가 만들 로봇에 필요한 수이므로 사용자가 지정한다.
  - 노드ID는 1~8만 유효하다. 출하 기본값(0x00)는 "미할당" 상태이므로 이 값으로는
    고정형 연결을 할 수 없고, 통신방식 세팅 단계에서 1~8 중 하나로 저장된다.
  - 그룹번호는 여러 로봇유닛이 함께 있을 때, 각 로봇유닛 안의 BLE 큐브끼리만
    혼선 없이 연결되도록 구분하는 가상 번호이다.

================================================================================
5. R큐브 초기 상태 및 전원/연결 동작
================================================================================

[출하 기본값]
  - 그룹번호 = 0 (지정안됨)
  - 노드ID   = 0 (미할당)
  - CMF      = 0 (BLE)        <- ★공장 출하 시 모든 큐브는 BLE 통신
  - ECF      = 0 (일반)
  ※ 노드ID=0(미할당)이므로 '비고정형' 상태이다.
  - 종단 스위치 = OFF          <- 기본은 종단 분리 (13장 참조)

[전원 버튼 동작]   ★설정 모드 / 셧다운(종료) 동작 정의
  - (꺼짐) 한 번 누름 : 전원 ON -> 대기모드 진입
  - (꺼짐) 짧게 두 번 누름 : 전원 ON 후 연결모드까지 진입

  ● 대기모드 (전원 ON, 아직 연결 전)에서의 버튼 동작
    - 짧게 다시 누름 : 연결모드로 전환
        · ECF=1 큐브는 연결모드에서 곧바로 edge central 역할을 시작한다.
        · ECF=0 · CMF=0(BLE) 큐브는 BLE 브로드캐스팅(RCUBEROBOT)을 시작해 상위 연결을
          기다린다. 즉 BLE 큐브에만 이 버튼 조작이 필요하다.
        · ECF=0 · CMF=1(CAN) 큐브는 ★버튼이 필요 없다 — 전원이 켜진 순간부터 부팅
          알림/하트비트를 발행하고 있으므로 이미 연결 대기 상태다. 눌러도 무해하다.
          (2026-08-03 개정. 5장 [연결모드 진입 동작 - CMF=1] 참조)
    - 길게(3초 이상) 누른 뒤 놓음 : BLE 설정 모드(Config Mode)로 진입
        · ECF/CMF/노드ID 저장값과 무관하게 BLE로 브로드캐스팅하여 외부(PC/앱)에서
          연결·재설정할 수 있게 한다. (*edge central 역할로 시작하지 않는다.)
    - 아주 길게(10초 이상) 누름 : 셧다운(종료) — 큐브가 안전 종료 후 전원을 내린다.  ★신규

  ● 연결 완료 상태 (연결모드에서 상위와 연결됨)에서의 버튼 동작
    - 길게(3초 이상) 누름 : 셧다운(종료).  ★신규
        · 운영 중 재설정을 막기 위해 설정 모드로 가지 않고 곧바로 종료한다.
        · 연결 상태에서는 10초를 기다릴 필요 없이 3초로 곧장 종료로 분기한다.

  ※ 상태별 롱프레스 요약
      - 미연결(대기모드) : 3초 = 설정 모드,  10초 = 셧다운(종료)
      - 연결 완료        : 3초 = 셧다운(종료)

[설정 모드 (Config Mode)]
  목적
    - edge central(ECF=1)로 세팅된 큐브는 연결모드에 들어가면 곧바로 central 역할을
      시작하므로, 이 큐브를 일반 큐브로 되돌리거나(ECF 해제) 노드ID/CMF/미션코드/
      펌웨어를 다시 설정할 정상 경로가 없다. 설정 모드는 ECF/CMF/노드ID 저장값을 무시하고
      외부에서 연결할 수 있게 하여 이 문제를 해결하는 "재설정/복구 진입점"이다.
    - edge central이 아닌 일반 큐브에서도, CMF가 CAN으로 저장돼 평소 BLE로 잡히지 않는
      큐브를 재설정할 때 동일하게 쓸 수 있다(설정 모드는 항상 BLE로 광고하므로).

  진입 방법
    - 전원을 켜 대기모드로 둔 상태에서, 버튼을 3초 이상 길게 누른 뒤 놓는다.
      (꺼진 상태에서 한 번 눌러 켠 뒤, 두 번째 누름을 3초 이상 길게 눌렀다 놓아도 된다.)
    - ★단, 연결 완료 상태에서는 3초 롱프레스가 셧다운으로 동작한다. 따라서 설정 모드
      진입은 대기모드(미연결) 상태에서만 가능하다.
    - 구현: 대기모드에서 버튼 down 시점부터 시간을 재고, release 시 누른 시간이
      3초 이상이면 설정 모드, 미만이면 연결모드로 분기한다. 3초에 도달하는 순간
      LED를 설정 모드 표시 패턴으로 바꿔, 사용자가 놓을 시점을 알 수 있게 한다.

  동작
    - ECF 무시 : edge central 역할을 시작하지 않는다(중앙 제어/미션 실행 안 함).
    - CMF 무시 : 저장값이 CAN이어도 BLE로만 브로드캐스팅한다. (CAN 버스·종단을 다시
      깔지 않고도 PC/앱이 항상 도달할 수 있게 하기 위함. 종단 스위치는 OFF 유지.)
    - 모터 중립 : 모션 루프는 목표를 받지 않고 정지 상태를 유지한다(안전).
    - BLE 광고 이름 : RCUBECONFIG.GG.NN (일반 연결모드의 RCUBEROBOT.GG.NN과 구분).
      PC/앱은 이 이름으로 설정 모드 큐브를 식별해 연결한다.

  설정 모드에서 가능한 작업 (PC/앱이 연결 후 수행)
    - ECF 해제(강등) : ECF 1->0.
        · 역할만 강등 : ECF만 0으로(노드ID/CMF/미션코드 유지) -> 같은 유닛의 일반
          멤버(노드 1)로 재사용. (ECF=0에서는 미션코드가 실행되지 않고 보관만 되며,
          나중에 다시 ECF=1로 승격하면 그 미션코드를 그대로 재사용할 수 있다.)
        · 완전 초기화(factory reset) : 노드ID=0x00, CMF=0(BLE), ECF=0, 종단 OFF,
          미션코드·멤버 맵 삭제 -> 출하 기본값.
    - 노드ID/CMF 재설정, 그룹번호 변경, (edge central이면) 멤버 맵 재설정.
    - 미션코드 교체/삭제, 펌웨어 OTA 갱신.
    - 적용 후 재부팅하면 새 설정으로 동작한다.

  표시 (LED/소리)
    - LED : 설정 모드임을 알리는 구분된 패턴(예: 노드ID 표시용 LED를 흰색 빠른 점멸
      0.25초 주기 — 연결대기의 1초 점멸과 구분). 그룹번호 표시용 LED는 평소대로
      그룹번호를 표시한다.
    - 소리 : 설정 모드 진입 시 전용 멜로디를 연주한다.

  안전/게이팅
    - 설정 모드는 미션을 실행하지 않고 모터를 움직이지 않으므로, 동작 중 오진입에 의한
      위험이 없다.
    - ECF 해제 등 재설정 명령은 설정 모드(또는 대기/연결대기)에서만 수용하고, armed/실행
      상태에서는 거부한다. (12.7 상태 머신과 정합)
    - 무선으로 재설정을 허용하므로 접근 제어가 필요하다(부록 [F] 참조). 물리 버튼
      제스처(3초)가 1차 게이트(물리 접근 필요) 역할을 한다.

[셧다운 모드 (Shutdown)]   ★신규
  목적
    - 사용자가 물리 버튼으로 큐브를 안전하게 종료(전원 차단)하는 정상 경로.

  진입 방법 (연결 상태에 따라 임계가 다름)
    - 대기모드(미연결) : 버튼 10초 이상 롱프레스.
    - 연결 완료 상태   : 버튼 3초 이상 롱프레스.
    - 구현: 버튼 down 시점부터 시간을 재고, 현재 연결 상태에 따른 임계(미연결 10초 /
      연결 3초)를 넘으면 셧다운으로 분기한다. 임계 도달 순간 LED를 종료 표시 패턴으로
      바꿔 사용자가 놓을 시점을 알 수 있게 한다.

  동작 (안전 종료, graceful)
    - 모터를 중립/파킹으로 전환하고, 필요한 상태 저장 및 연결 정리(상위/멤버에 링크
      종료 통지)를 마친다.
    - 이후 전원유지 신호 PWR_HOLD(전원버튼 컨트롤러 STM6601의 PSHOLD)를 해제(Low)하면
      STM6601이 EN을 내려 메인 전원이 차단된다. (상시-온 대기바이어스 LR8 +3V3_SB는 유지)
    - ※ STM6601의 하드웨어 자체 롱프레스(강제OFF/RST)는 SR핀을 +3V3_SB로 고정해
      비활성화되어 있다. 따라서 3초/10초 등 버튼 타이밍 판정은 전적으로 펌웨어가
      버튼상태(PBOUT)·인터럽트(INT)로 측정하고, 종료도 펌웨어가 PWR_HOLD 해제로 수행한다.
    - PWR_HOLD 극성: High = 전원 유지, Low = 전원 차단.

  표시 (LED/소리)
    - 종료 진입 시 전용 종료 멜로디와 LED 종료 패턴으로 알린 뒤 전원을 내린다.

  안전
    - 연결 상태에서는 3초 롱프레스로 곧장 종료되므로 운영 중 실수로 설정 모드에 빠지지
      않는다. 미연결 상태에서는 3초=설정 모드가 우선이고 10초에서 종료로 분기한다.

[칼라 LED 종류]
  - R큐브에는 2종류의 칼라 LED가 있다.
  - 가장 많이 사용하며 큐브의 2변에 위치하여 눈에 잘 보이는 칼라 LED는 노드ID를
    보여주는 데 사용한다.
  - R큐브 전원버튼 근처에 있는 칼라 LED는 주로 BLE 연결 혼선을 방지하기 위한
    그룹번호를 표시하는 데 사용한다.

[ID 표시용 칼라LED 점등 규칙]   ★혼합/리드/허브 + 가상 노드ID 반영
  ※ ★2026-07-29: **노드ID를 나타내는 유일한 수단은 이 LED다.** 소리(멜로디)에는
    노드ID를 싣지 않는다([소리 규칙] 참조).
  - 멤버 큐브이고 대기 모드이거나, 연결모드이긴 하나 상위(서브: PC/BLE 허브, 독립:
    edge central)에 연결이 완료되지 않은 상태인 경우
    * 고정형(플래시에 노드ID 저장됨)이면 해당 저장 노드ID 색상으로 1초 주기 점멸한다.
    * 비고정형(노드ID 미할당)이면 상위에 연결되기 전까지 흰색으로 1초 주기 점멸한다
      — 통신방식 세팅 전 초기 구성 단계가 여기에 해당한다.
  - 멤버 큐브이고 상위에 연결이 완료된 경우
    * 고정형이면 저장 노드ID 색상으로 상시 점등한다.
    * ★비고정형이면 상위(PC/허브)가 연결 순서로 배정한 "가상 노드ID"의 색상으로 상시
      점등한다(첫 큐브=가상1=Red, 다음=가상2=Green …). 이 색은 저장되지 않으며, reset
      후 다시 흰색 점멸로 돌아간다.
  - BLE 허브 큐브인 경우
    * ★비고정형 초기 구성: PC에 처음 연결된 큐브가 가상1이 되어 Red로 멀티롤(허브)을
      시작한다. 담당 BLE 멤버가 모두 연결되기 전엔 Red 점멸(1초), 모두 연결되면 Red 상시
      점등한다.
    * 고정형(서브 전용): BLE 세팅 큐브 중 최소 노드ID 큐브가 허브가 되며, 자신의 저장
      노드ID 색상으로 (연결 완료 전 점멸 → 완료 시 상시 점등)한다. (무조건 빨강 아님)
  - edge central 큐브(노드01)인 경우
    * 멤버가 모두 연결되기 전까지는 Red 점멸(1초 주기)하다가 모두 연결되면 Red 상시
      점등. (노드 01이므로 Red)
  - 설정 모드(Config Mode)인 경우
    * 흰색 빠른 점멸(0.25초 주기)로 설정 모드임을 표시한다(위 1초 점멸들과 구분).

[그룹번호 표시용 칼라 LED 점등 규칙]
  - 큐브 전원이 켜져 있는 한 이 LED는 그룹번호를 색상으로 표시한다.
    (그룹번호가 없는 경우 흰색으로 점멸)

[소리 규칙]   ★혼합/리드/허브/설정모드 반영 · ★2026-07-29 재정의

  ※ 역할 분담(중요): **노드ID는 소리에 반영하지 않는다.** 노드ID는 ID 표시용 칼라
    LED로만 나타내고, 소리는 "상태가 바뀌었다"를 알리는 데 쓴다. 같은 값을 두 경로로
    이중 표시하면 한쪽 규칙만 바뀌었을 때 서로 어긋나기 때문이다.
    그룹번호만 예외로 소리에 실린다 — BLE 연결 혼선을 막기 위해 사용자가 그룹을
    귀로도 확인할 수 있어야 하고, 그룹 LED와 같은 자릿수를 쓰므로 어긋나지 않는다.

  - 전원이 켜질 때는 노드ID와 무관하게 START(부팅/시작음) 멜로디를 **1회** 연주한다.
    ★2026-07-30: 재생 속도를 2배로 한다 — B3 0.25초 → D4 0.25초 → B4 0.5초, 총 1초.
    (음·순서는 큐브_멜로디_데이터.xlsx '멜로디 데이터'와 같고 길이만 절반이다.)
  - ★2026-07-30 BLE 연결이 끊기면 START를 **역순**으로 연주한다.
    (B4 → D4 → B3, 세 음 모두 0.25초로 균등. 총 0.75초)
    붙을 때는 상행, 떨어질 때는 하행이므로 연결 상태 변화를 귀로 바로 구분할 수 있다.
  - 버튼을 누를 때(눌림 감지 시점)
       · 그룹번호 미배정(0) : 버튼눌림음(BUTTON_PRESSED)을 연주한다.
       · 그룹번호 배정됨(1~99) : 그룹번호 두 자리를 음으로 알린다. 십의 자리를 0.2초,
         일의 자리를 0.6초 연주한다. 자릿수→음은 그룹 LED 색상표와 같은 순서다.
              0 흰색   C4        5 Magenta A4
              1 Red    D4        6 Yellow  B4
              2 Green  E4        7 Violet  C5
              3 Blue   F4        8 Orange  D5
              4 Cyan   G4        9 연한Red E5
         (예: 그룹 12 → 십의자리 1=Red=D4 0.2초, 일의자리 2=Green=E4 0.6초)
         ※ 기존 PINGPONG의 DiscoveryGroupIdSound와 같은 방식이다(자릿수+2를 음
           인덱스로). 다만 그쪽은 16진 니블, 여기서는 그룹 LED와 맞추려고 10진 자리를 쓴다.
  - 켜진 상태에서 버튼을 눌러 연결모드로 갈 때 자신이 edge central이면 엣지 멜로디를,
    멤버 큐브이면 연결대기 멜로디를 연주한다.
  - 버튼을 길게 눌러 설정 모드로 진입할 때는 설정 모드 진입 멜로디를 연주한다.
  - edge central 큐브는 모든 멤버 연결이 완료되면 유닛구성완료멜로디를 연주한다.
  - BLE 허브 큐브(서브 전용)는 자신이 담당하는 BLE 분기의 멤버가 모두 연결되면
    (BLE 분기 한정) 유닛구성완료멜로디를 연주한다. (서브로봇유닛의 전체 완료 판단은
    PC가 한다.)
  - 유닛을 구성하는 R큐브의 오류로 정지하는 경우, 네트워크에서 끊어지는 모든 큐브는
    오류멜로디를 연주한다.

[연결모드 진입 동작 - ECF = 0 (일반 큐브), CMF로 분기]
  - CMF=0 (BLE 세팅 큐브)
       · BLE 브로드캐스팅 시작 : RCUBEROBOT.GG.NN  (GG=그룹번호, NN=노드ID)
       · 서브: PC 또는 BLE 허브 큐브가 / 독립: edge central이 노드ID 순서대로 이
         큐브를 연결한다.
  - CMF=1 (CAN 세팅 큐브)   ★버튼 조작 불필요 (2026-08-03 개정)
       · 전원이 켜지면 연결모드 진입 버튼을 누르지 않아도 부팅 알림(NodeAnnounce)을
         한 번 보내고 이어서 1초 주기 하트비트를 계속 발행한다. 즉 CAN 큐브는
         "전원 ON = 연결 대기"이며, 별도의 연결모드 전환 동작이 없다.
         (BLE처럼 광고를 켜고 끄는 개념이 없고, 하트비트는 버스에 늘 흐른다.)
       · 서브: PC(USB-CAN)가 / 독립: edge central(CAN)이 노드ID 순서대로 직접 연결한다.
       · 큐브는 상위(PC/edge central)가 자기에게 보낸 첫 프레임을 받은 시점을 연결
         성립으로 보고, 연결음 + 자기 노드ID 색 상시 점등으로 전환한다.
       · 버튼은 설정 모드 진입(3초)·셧다운(10초)에만 쓴다. 대기 상태에서 짧게 눌러도
         CAN 큐브에는 바뀌는 것이 없다(무해).
  - 고정형이라 큐브는 자기 노드ID를 이미 알고 있으므로, 연결 완료 시 자기 노드ID
    색상으로 LED를 스스로 켠다. 상위(독립: edge central / 서브 BLE: BLE 허브 / 서브
    CAN: PC)는 연결을 확인할 뿐이며, 필요 시 색상 확인 명령만 보낸다.
  - ★CAN 큐브의 종단은 연결 시점이 아니라 부팅 시점에 이미 결정된다. 종단노드ID는
    통신방식 세팅 저장 단계(7.2/7.3)에서 각 CAN 큐브 플래시에 미리 기록되어 있으므로,
    CMF=1인 큐브는 부팅 시 자기 노드ID == 종단노드ID이면 CAN 통신 없이 스스로 종단
    스위치를 켜서 CAN 버스 끝을 닫는다. (반대쪽 끝: 독립=edge central(노드01)이 자기
    맵으로 자가 종단, 서브=PC USB-CAN 어댑터. 13장)
  - (서브 BLE 분기) PC에 BLE로 처음 연결되는 BLE 세팅 큐브(최소 노드ID)가 PC에 의해
    BLE 허브 큐브로 지정되고, PC로부터 "BLE로 세팅된 큐브 수"를 받아 나머지 BLE
    멤버를 모두 연결한다. (독립로봇유닛에는 해당 없음 - edge central 직접 연결)

[연결모드 진입 동작 - ECF = 1 (edge central 큐브 = 리드 큐브/노드01)]   ★서버선택/직접연결
  - 스스로 edge central로 동작을 시작하고, 저장된 "멤버별 {노드ID, CMF} 맵"을 참조해
    필요한 통신 서버만 켠다.
       · 멤버가 CAN만 사용 -> CAN 서버(TWAI 스택)만 실행
       · 멤버가 BLE만 사용 -> BLE 서버(NimBLE central)만 실행
       · CAN/BLE 혼합     -> 두 서버를 동시에 실행
  - 이어서 노드ID 순서대로, 각 멤버의 통신방식(CMF)에 맞게 신호를 주고받아 연결한다.
       · CAN 멤버 : CAN 부팅/하트비트 신호로 해당 노드ID를 확인해 연결한다.
       · BLE 멤버 : ★edge central이 BLE scan으로 각 BLE 멤버에 직접 연결한다(NimBLE
                    central 다중 연결). BLE 허브 큐브를 거치지 않는다.
                    ※ BLE 멤버 연결은 전원 켜는 순서와 무관하다. 연결 순서는 스캐너인
                      edge central이 정하며, 각 멤버는 광고에 실린 노드ID로 식별·매핑한다
                      (RCUBEROBOT.GG.NN). 멤버는 연결될 때까지 계속 광고하고, edge
                      central은 기대 노드ID가 모두 연결될 때까지 스캔하며, 빠진 노드ID는
                      타임아웃/재시도로 처리한다.
  - 멤버 맵에 있는 모든 노드ID가 각자의 통신방식대로 연결되면 미션코드 실행으로 넘어간다.
  - ※ edge central로 세팅된 큐브를 일반 큐브로 되돌리려면, 연결모드 대신 설정 모드로
    진입시켜(버튼 3초 롱프레스) PC/앱에서 ECF를 해제한다. (위 [설정 모드] 참조)

6. 로봇 구성 예시
================================================================================

  - 이송 로봇 (R1)
    R큐브 1개에 홀더링크를 달아 홀더에 물체가 올려지면 링크를 회전하여 물체를
    옮기는 로봇.

  - 자동차형 로봇 (R2)
      R큐브 2개를 PC에 연결, 자동차 형태의 링크를 구성해 양쪽에 큐브를 붙이고
      회전면에 바퀴를 장착하면 제어 프로그램으로 자동차 로봇을 구동할 수 있다.
      -> 리드 큐브(노드 01)에 미션코드를 업로드하고 독립로봇유닛 모드로 설정하면,
         PC와 끊겨도 R큐브끼리 연결되어 저장된 미션코드를 수행한다.

  - 배송 로봇 (R3)
      R큐브 2개는 자동차 바퀴, 1개는 로봇집게를 장착하여 배송 로봇을 구현할 수 있다.

  - 스카라 로봇 (R4)
      R큐브 4개로 스카라 로봇을 구성하여 원하는 스카라 동작을 구현할 수 있다.

  - 혼합 통신 예시 (R3)
      노드 01(CAN), 노드 02(CAN), 노드 03(BLE)로 세팅하면, 서브에서는 노드01·02가
      PC에 CAN으로 직접 붙고 노드03은 BLE 허브 큐브(여기서는 노드03 자신)를 통해
      BLE로 붙는다. 독립으로 전환하면 edge central(노드01)이 노드02를 CAN으로, 노드03을
      BLE로 직접 연결한다(허브 없음). 케이블 배선이 어려운 끝단 그리퍼만 BLE로 두고
      본체 축은 CAN으로 묶는 식의 구성이 가능하다.

  - 전체 공정 라인 (다중 서브로봇유닛)
      PC 1대 + 다중 USB-CAN으로 위와 같은 서브로봇유닛(이송/배송/스카라 등, 각자
      CAN/BLE 혼합 가능)을 유닛마다 묶어 하나의 공정 라인으로 구성할 수 있다. (3장)

7. 연결 절차
================================================================================

새 기획에서는 "모든 큐브를 일단 BLE 비고정형으로 PC에 연결"한 뒤, "큐브별 통신방식
세팅"을 거치는 흐름이 표준이다. 통신방식 세팅에서 저장을 누르는 순간 노드ID/CMF가
함께 저장되어 고정형이 된다(7.5).

--------------------------------------------------------------------------------
7.1 공통 1단계 - 비고정형 BLE로 전체 구성
--------------------------------------------------------------------------------
  ※ 큐브별 통신방식을 지정하려면, 먼저 PC 제어 프로그램에 로봇시스템에 필요한
     R큐브들을 모두 BLE로 연결한 상태여야 한다. (출하 기본 CMF=0 BLE 이용)
  ※ 이 단계는 비고정형(BLE) 연결순서 모드로 진행한다. 노드ID는 아직 미할당(0x00)이며,
     PC에 연결되는 순서에 따라 상위가 가상 노드ID(1..N)를 배정한다(저장하지 않음).
  ※ 연결 순서를 정하는 두 가지 옵션:
       (A) 사용자 지정 순서(초기 구성 기본) : 사용자가 큐브들의 순서를 정해, 그 순서대로
           하나씩 전원(버튼)을 켜서 PC에 연결한다. 연결 순서 = 가상 노드ID = 색상.
       (B) 저장 노드ID 순서 자동(재구성 시) : 이미 노드ID가 저장된 큐브라면 광고의 노드ID로
           식별되어, 켜는 순서와 무관하게 PC가 노드ID 순으로 자동 연결한다(고정형, 7.5).
  ※ 이 단계에서는 종단이 필요 없다(아직 CAN 미사용). 모든 큐브 종단 OFF.
  ※ 이미 ECF=1(edge central)나 CMF=CAN으로 저장돼 BLE로 잡히지 않는 큐브가 섞여 있으면,
     해당 큐브를 설정 모드(버튼 3초 롱프레스)로 진입시켜 먼저 BLE로 연결·초기화한 뒤
     이 단계를 진행한다. (5장 [설정 모드])

  1) PC 제어 프로그램을 비고정형(BLE) 연결 모드로 진행한다.
  2) 로봇을 설계한 사용자가 각 R큐브의 역할 순서를 고려하여, 순서를 정해 R큐브를
     하나씩 PC에 BLE로 연결한다. 각 큐브는 연결 전 흰색 점멸하다가, 연결되어 가상
     노드ID가 배정되면 그 색으로 점등한다(첫 큐브=가상1=Red, 다음=가상2=Green …).
       · ★PC에 처음 연결된 큐브는 가상1(Red)이 되며, PC가 이 큐브를 BLE 허브(멀티롤)로
         런타임 지정한다. 이 허브가 나머지 BLE 멤버를 연결 순서대로 취합하고, 연결되는
         순서에 따라 가상2·3·… 가 배정되어 각 큐브가 해당 색으로 점등한다.
       · 사용자는 큐브 LED 색으로 현재 연결 순서(가상 노드ID)를 눈으로 확인할 수 있다.
  3) 필요한 모든 R큐브가 PC에 연결되면 "서브로봇유닛"이 임시 구성된 것이다.
     -> 이 상태에서 7.2(세팅만) 또는 7.3(세팅+독립전환)으로 진행한다.

--------------------------------------------------------------------------------
7.2 큐브별 통신방식 세팅 (서브로봇유닛 유지)
--------------------------------------------------------------------------------
  ※ 전제: 7.1로 비고정형 BLE 서브로봇유닛이 구성된 상태.

  1) PC 제어 프로그램에서 "큐브별 통신방식 지정 세팅 화면"으로 들어간다.
  2) 사용자가 각 큐브를 CAN 또는 BLE로 선택하고 "저장"한다.
     -> PC는 각 R큐브에 명령을 주어, 다음을 함께 플래시에 저장하게 한다.
          · CMF (선택한 통신방식: 0=BLE / 1=CAN)
          · 노드ID (현재 연결 순서값)
          · ★(CMF=1 큐브만) 종단노드ID (= 이 유닛에서 CAN으로 세팅된 큐브 중 최대
            노드ID). PC가 전체 선택 결과에서 산출해 각 CAN 큐브 플래시에 기록한다.
            -> 이후 reset/부팅 시 각 CAN 큐브가 자기 노드ID==종단노드ID 비교로 자가
               종단을 결정한다(CAN 통신 불필요). (13장)
       ※ 노드ID가 저장되는 순간 곧 고정형이다(별도 고정형 전환 명령 없음;
         노드ID 할당 여부로 고정형/비고정형 판정).
       ※ 미선택 큐브의 기본값은 BLE(CMF=0)이다.
  3) PC 제어 프로그램은 각 R큐브의 노드ID와 세팅된 통신방식을 매칭해 자신의 메모리에
     저장(매핑 테이블)한다. — 이후 고정형 재연결 시 어떤 큐브를 CAN/BLE로 붙일지
     판단하는 근거가 된다. (이 매핑 테이블은 7.3 독립 전환 시 edge central에 저장될
     "멤버 맵"의 원본이기도 하다.)
  4) 위 저장이 완료되면 PC 제어 프로그램은 모든 R큐브에 reset 명령을 준다.
  5) 사용자는 CAN으로 세팅한 큐브들을 PC(USB-CAN)와 큐브들끼리 CAN 케이블로 미리
     연결해 둔다. (CAN 분기 물리 배선)
       · ★배선 순서: CAN 큐브를 노드ID 오름차순 데이지체인으로 잇고, 종단 큐브를 양 끝에
         둔다 — PC USB-CAN 어댑터(한쪽 끝) + 최대 CAN 노드ID 큐브(반대쪽 끝). (13장 [CAN 배선 순서])
  6) PC 제어 프로그램을 고정형 연결 모드로 전환한다.
  7) PC는 자신의 매핑 테이블을 참조해 통신방식별로 큐브를 연결한다.
       [CAN 분기]
         · PC USB-CAN 어댑터의 종단을 ON으로 둔다(버스 한쪽 끝).
         · CAN으로 연결해야 할 큐브들을 노드ID 순서대로, 부팅/하트비트 신호 확인을
           통해 연결한다.
         · 종단은 이미 끝나 있다: 각 CAN 큐브는 reset 후 부팅 시 자기 플래시의 종단노드ID
           (2단계에서 기록)로 자가 종단되어 있고, PC USB-CAN 어댑터는 내장 종단 ON.
           PC는 노드ID 순서로 연결만 한다. (13장)
       [BLE 분기]
         · BLE로 세팅된 큐브 중 최소 노드ID 큐브가 PC에 BLE로 가장 먼저 연결되며,
           PC가 이 큐브를 BLE 허브 큐브(multirole)로 지정한다.
         · ★이 BLE 허브 큐브는 기존처럼 무조건 Red가 아니라, 자신의 노드ID 색상으로
           켜진다.
         · PC는 BLE 허브 큐브에게 "BLE로 세팅된 큐브 수"를 전달하고, BLE 허브 큐브가
           나머지 BLE 멤버들을 노드ID 순서대로 모두 연결한다.
  8) 각 큐브의 연결모드 신호 발행 방식(5장과 동일)
       · CMF=0(BLE) 큐브 : 켜진 후 버튼으로 연결모드에 넣으면 자신을 BLE
         브로드캐스팅하여 PC/BLE 허브가 연결하게 한다.
       · CMF=1(CAN) 큐브 : ★전원만 켜면 된다. 부팅 알림/하트비트를 자동으로 발행하므로
         버튼 조작 없이 PC가 노드ID 순서대로 연결한다. (2026-08-03 개정)
         -> 실제 사용에서도 CAN 분기는 "전원 켜고 PC에서 고정형 연결"만으로 끝난다.

  ※ 용어 정리(중요): 위와 같이 CAN/BLE가 혼합되면 "하나의 aggregator central이 모든
     멤버를 취합"한다는 개념이 성립하지 않는다. 따라서
        · 노드 01 큐브 = 리드 큐브(독립 전환 시 edge central)
        · BLE 분기 취합자(서브 전용) = BLE 허브 큐브(BLE 세팅 큐브 중 최소 노드ID)
     로 분리해 부른다. CAN 분기는 PC가 직접 취합하므로 별도 중계 큐브가 없다.

--------------------------------------------------------------------------------
7.3 큐브별 통신방식 세팅 + 독립로봇유닛 전환
--------------------------------------------------------------------------------
  ※ 전제: 7.1로 비고정형 BLE 서브로봇유닛이 구성된 상태.

  1) PC 제어 프로그램의 큐브별 통신방식 세팅 화면에서 각 큐브의 통신방식을 정하면서
     "고정로봇유닛(독립)" 체크박스를 체크한다.
  2) 체크하면 PC가 사용자에게 미션코드를 요청한다. 사용자가 미션코드를 올리면 PC는
     리드 큐브(노드 01)에 미션코드를 업로드한다.
  3) 업로드가 완료되면 PC는 각 큐브가 다음을 플래시에 저장하도록 명령한다.
        · CMF (선택한 통신방식)
        · 노드ID (연결 순서값)   ※ 노드ID 저장 = 고정형
        · ★(CMF=1 큐브만) 종단노드ID (= CAN 세팅 멤버 중 최대 노드ID). PC가 전체
          맵에서 산출해 각 CAN 큐브 플래시에 기록한다. -> 부팅 시 자기 노드ID==종단노드ID
          비교로 자가 종단(13장).
        · 리드 큐브(노드 01)에는 추가로 다음을 저장한다.   ★보강 (멤버 맵)
            - ECF = 1
            - 전체 큐브 수 N
            - ★멤버별 {노드ID, CMF} 맵 : PC가 7.2/7.3에서 만든 매핑 테이블(어느
              노드ID가 CAN인지 BLE인지)을 그대로 리드 큐브에 전달해 저장한다.
              -> edge central이 부팅 시 이 맵을 보고 (a) 어느 멤버를 CAN/BLE로 연결할지,
                 (b) CAN 서버/BLE 서버 중 무엇을 켤지(둘 중 하나만/둘 다)를 판단한다.
            - 종단노드ID (= CAN 세팅 멤버 중 최대 노드ID). edge central은 이 값을 자기
              끝(노드01) 종단 판단과 13장 산출에 쓴다. (맵에서 직접 계산해도 된다.)
  4) 저장이 완료되면 PC는 모든 R큐브에 shut down 명령을 주어 모두 끈다.
  5) 모두 꺼졌을 때 배선을 독립로봇유닛 형태로 정리한다.
        · PC와 리드 큐브(노드 01) 사이에 CAN 케이블이 연결되어 있으면 제거한다.
          (이제 독립로봇유닛으로 동작하므로 PC가 버스에서 빠진다.)
        · CAN으로 세팅된 R큐브들과 리드 큐브(=edge central)를 CAN 케이블로 서로
          연결한다. ★노드ID 오름차순 데이지체인으로 잇고, 한쪽 끝 = edge central(노드01),
          반대쪽 끝 = 최대 CAN 노드ID 큐브가 되도록 배치한다. (13장 [CAN 배선 순서])
  6) R큐브들의 버튼을 2번 눌러 연결모드로 진입시킨다. 가급적 edge central(노드 01)을
     먼저 켠다.
  7) edge central(노드 01)은 저장된 멤버 맵({노드ID, CMF}, N, 종단노드ID)을 참조해
     필요한 통신 서버만 켜고(CAN만/BLE만/둘 다), 노드ID 순서대로 멤버를 연결한다.
        · CAN 멤버 : 네트워크에 해당 노드ID가 있는지 부팅/하트비트로 확인해 연결.
          종단은 부팅 시 이미 결정된다: 각 CAN 멤버는 자기 플래시의 종단노드ID로,
          edge central(노드01)은 자기 맵으로, 각각 부팅 시 양 끝을 자가 종단한다. (13장)
        · BLE 멤버 : ★edge central이 BLE scan으로 각 BLE 멤버에 직접 연결한다(NimBLE
          central 다중 연결). 독립로봇유닛에는 BLE 허브 큐브가 없다.
  8) 필요한 모든 멤버가 연결되면 edge central에 저장된 미션코드가 실행되어, 자신을
     포함한 모든 R큐브가 미션을 수행한다.

  [독립 -> 일반/서브 되돌리기]   ★설정 모드 활용
    - 독립로봇유닛의 edge central(ECF=1)을 다시 일반 큐브로 되돌리려면, 그 큐브를 설정
      모드(버튼 3초 롱프레스)로 진입시켜 PC/앱에서 ECF를 해제(강등)한다.
      (역할만 강등 또는 완전 초기화 선택. 완전 초기화 시 멤버 맵도 삭제. 5장 [설정 모드])

  [노드ID/세팅 초기화 - 공통]
    - PC(또는 전용 앱)가 초기화 명령을 내리면 각 R큐브는 노드ID=0x00, CMF=0(BLE),
      ECF=0, 종단 스위치 OFF로 되돌린다(출하 기본값). 노드ID=0x00이므로 비고정형
      상태가 된다. edge central은 멤버 맵도 함께 삭제한다.
    - 멤버 큐브(ECF=0)는 서브 연결 상태에서 이 명령을 받을 수 있다. edge central
      (ECF=1)처럼 연결모드에서 곧바로 central이 되어 버리는 큐브는, 설정 모드로
      진입시켜 초기화한다.

--------------------------------------------------------------------------------
7.4 독립로봇유닛 동작순서 (혼합 통신)
--------------------------------------------------------------------------------
  1) 구성 R큐브들을 꺼진 상태에서 전원 버튼을 두 번 눌러 연결모드로 진입시킨다.
     (edge central을 먼저 켜는 것을 권장)
  2) ECF=1인 큐브(리드 큐브/노드01)는 스스로 edge central 모드로 시작한다.
  3) edge central은 reset 완료 후 ECF=1과 저장된 멤버 맵({노드ID, CMF}, N, 종단노드ID)을
     확인하고, 맵에 따라 필요한 통신 서버만 켠다.   ★서버 선택
        · CAN 멤버만 있으면 CAN 서버(TWAI)만, BLE 멤버만 있으면 BLE 서버(NimBLE)만,
          둘 다면 둘 다 켠다.
     그런 다음 노드ID 순서대로 각 멤버의 통신방식에 맞게 연결될 때까지 기다린다.
  4) 통신방식별 연결:
       · CMF=1 멤버(CAN): CAN 부팅/하트비트 신호로 노드ID가 모두 발견될 때까지
         기다려 연결한다.
           - 종단: 부팅 시 이미 결정되어 있다. 각 CAN 멤버는 자기 플래시의 종단노드ID와
             자기 노드ID를 비교해 같으면 종단 ON, edge central(노드01)도 자기 맵으로
             자가 종단 ON, 가운데 CAN 큐브는 OFF. (연결 시 종단노드ID 전달 불필요;
             edge central은 연결 시 노드ID 색상만 전달. 양 끝이 모두 큐브.) (13장)
       · CMF=0 멤버(BLE): ★edge central이 BLE scan으로 각 BLE 멤버에 직접 연결한다
         (NimBLE central 다중 연결). 독립로봇유닛에는 BLE 허브 큐브가 없다.
           - BLE 멤버 연결은 전원 켜는 순서와 무관하다. 연결 순서는 스캐너인 edge
             central이 정하며, 각 멤버는 광고에 실린 노드ID(RCUBEROBOT.GG.NN)로 식별·
             매핑한다. 멤버는 연결될 때까지 계속 광고하고, edge central은 기대 노드ID가
             모두 연결될 때까지 스캔하며, 빠진 노드ID는 타임아웃/재시도로 처리한다.
  5) 각 큐브는 고정형이라 자기 노드ID를 이미 알고 있으므로, 연결되면 자기 노드ID
     색상을 코너 LED에 스스로 표시한다(edge central은 연결된 노드ID 확인만).
  6) 필요한 모든 큐브가 연결되면 edge central에 저장된 미션코드가 실행되어, 자신을
     포함한 모든 R큐브가 미션을 수행한다.

7.5 고정형 / 비고정형 연결순서 흐름 (재정의)
--------------------------------------------------------------------------------
  [기존 방식]
    - 서브로봇유닛에서 PC가 비고정형(BLE)으로 R큐브를 연결하고 통신방식을 정한 뒤,
      "고정형 전환 명령"을 별도로 내리면 그때부터 R큐브들이 연결 순서를 기억해 BLE
      또는 CAN으로 고정형 연결되는 방식이었다.

  [새 방식]   ★변경
    - 비고정형(BLE)은 "통신방식 세팅 전 초기 구성" 단계로만 쓴다(노드ID 미할당). 이 단계
      에서는 PC에 연결되는 순서로 상위가 "가상 노드ID(1..N)"를 실시간 배정하며(저장 안 함),
      각 큐브는 가상 노드ID 색으로 점등한다(첫 큐브=가상1=Red=멀티롤 허브). 연결 순서는
      사용자가 큐브를 켜는 순서로 지정한다.
    - 통신방식 세팅에서 "저장"을 누르면, 그 시점의 가상 노드ID가 곧 저장 노드ID(1~8)로
      확정되어 플래시에 기록된다(= 고정형 전환).
    - 큐브별 통신방식 지정 세팅 화면에서 각 큐브의 BLE/CAN을 고르고 "저장하기"를
      누르는 순간, 각 큐브에 통신방식(CMF)뿐 아니라 노드ID가 함께 저장된다.
      -> 이 저장 동작(노드ID 저장) 자체가 곧 고정형이다. 별도의 고정형 전환 명령이
         필요 없다(노드ID 할당 여부로 고정형/비고정형 판정).
    - 이후 reset/재연결부터는 각 큐브가 저장된 노드ID/CMF에 따라 자동으로 고정형
      연결된다(서브: PC가 고정형 모드로 재연결 / 독립: edge central이 멤버 맵대로 연결).

  [요약]
    비고정형 BLE 초기 구성 -> 큐브별 통신방식 세팅 + 저장(= 노드ID/CMF 저장 = 고정형)
    -> reset -> 고정형으로 CAN/BLE 혼합 재연결.

================================================================================
8. 미션코드·로봇 제어 동작 (미션 / 태스크공간 / 제어 모드)
================================================================================

  - 미션코드는, 로봇유닛이 독립로봇유닛일 때 edge central 큐브(=리드 큐브/노드01)에
    저장된 코드를 의미한다.
  - 미션코드의 형태는 2가지이며, 두 형태 모두 edge central이 중앙 제어 방식으로
    로봇유닛을 제어한다(CAN 멤버는 CAN으로, BLE 멤버는 BLE 직접 연결로 분배).
       (1) 데이터 테이블 형태
             각 큐브별 동작 데이터를 저장한 테이블. edge central이 이 테이블을
             참조하여 (반복 또는 지정 횟수) 로봇유닛을 중앙 제어한다.
       (2) 마이크로파이썬 코드 형태
             R큐브에 마이크로파이썬이 설치되어 있으며, 사용자가 작성한 파이썬 코드를
             edge central에 업로드하면 edge central이 이를 실행하여 로봇유닛을
             제어한다.
  - ★제어 계층 구분(중요): 미션코드(데이터 테이블/파이썬)는 "무엇을, 언제"를 정하는
    상위 시퀀싱이며, edge central은 이를 풀어 각 큐브에 20~50Hz 키프레임(목표위치+
    도달시간/속도)으로 분배할 뿐이다. 실제 모터의 실시간 제어(1kHz 이상 서보 루프)와
    키프레임 간 보간은 각 큐브의 STM32G4-가 전담한다. 즉 미션코드는 실시간 제어
    루프가 아니다. (11장, 12.9 참조)

[태스크공간 제어 (IK/FK) - edge central이 직교좌표를 관절공간으로 분해]   ★산업용
  - R큐브 로봇은 관절공간(각 큐브의 목표 각도)뿐 아니라 직교좌표(X, Y, Z, 회전 R) 목표로도
    제어할 수 있다. 예: 스카라 로봇에게 "TCP(손끝)를 (x, y) 위치로 이동"을 직접 지시.
  - 변환 주체 = edge central(대표/노드01). edge central은 로봇의 기구학 모델을 갖고,
    직교좌표 목표를 역기구학(IK)으로 각 축의 관절 각도로 분해해, 관절공간 키프레임으로 각
    큐브(자신 포함)에 분배한다. 역방향(현재 관절각 -> TCP 위치)은 순기구학(FK)으로 계산해
    위치 조회에 답한다.
  - 기구학 모델은 로봇 구성에 따라 설정한다: 유형(직교 XYZ 테이블 / SCARA 등), 축 수,
    축<->노드ID 매핑, 링크 길이/리드 등 파라미터. (1~4 DoF 템플릿 기준으로 해석적 폐형 IK를
    edge central ESP32에서 실시간 수행. 충돌 회피 같은 복잡한 경로계획은 오프라인/상위에서.)
  - 좌표 목표는 즉시 이동, 또는 여러 웨이포인트를 실은 경로(스케줄)로 줄 수 있다. edge
    central이 이를 다축 관절 키프레임 + 공통 시각 T0로 풀어 동기 출발시킨다.
  - 단위: 위치 0.01mm, 회전 0.01°, 속도 = TCP 기준 mm/s(관절 속도가 아니라 손끝 속도).
  - BLE 프로토콜 대응: SetKinematicModel / SetWorkOrigin / MoveToPosition /
    SetScheduledPositions(직교 경로) + GetPosition(FK 조회). 대상 주소 = 대표(Hub 0xFE).
  ※ 개별 큐브는 여전히 관절공간(각도)으로만 동작한다. 직교<->관절 변환은 오직 edge central이
    담당하므로 멤버 큐브 펌웨어는 기구학을 몰라도 된다(구조 단순).

[R큐브 모터 제어 모드·파라미터 (산업용)]   ★산업용
  R큐브는 단순 위치 이동 외에도 산업용 서보 드라이브 수준의 제어 모드·파라미터를 지원한다.
  이 값들은 상위(미션코드/PC)가 설정하고, 실제 실행은 각 큐브의 STM32G4-가 전담한다.
  - 드라이브 상태 제어 : 모터 드라이브를 여자(Enable)/소자(Disable)/급정지(QuickStop)/
    폴트리셋(FaultReset)/정지대기(Halt)/일시정지·재개(Pause·Resume)로 전환한다(CiA 402류
    상태머신). 폴트로 트립되면 FaultReset로 복구한다.
  - 토크 제어 모드 : 위치·속도 대신 목표 토크를 직접 지령해, 힘 제어가 필요한 작업(집기
    파지력, 압입 등)에 쓴다.
  - ★순응 제어 / 직접교시(리드스루 티칭) : 모터를 순응(Compliant)/중력보상 모드로 두어,
    사용자가 로봇 팔을 손으로 잡고 움직여 경로를 가르칠 수 있다(강성/감쇠 파라미터 조절).
    가르친 경로를 미션으로 저장해 재생한다. 단, 유성기어의 백드라이버빌리티에 따라 구현
    수준이 달라지므로 상세 설계에서 확정한다.
  - 제어 게인 : 위치/속도/전류 루프의 PID 게인을 큐브별로 튜닝한다.
  - 모션 리밋 : 최대 속도·가속·저크 상한을 설정해 진동·오버슈트를 억제한다(11장 설계
    원칙의 런타임 설정판).
  - 폴트 임계 : 추종오차/과전류/과온 임계를 설정해, 초과 시 큐브가 스스로 폴트 정지한다.
  - 각도 소프트리밋 : 관절별 허용 각도 범위와 금지구간(k개)을 두어, 그 밖으로 나가는 목표를
    큐브가 거부한다(기구·배선 보호). edge central의 IK도 이 한계를 넘는 해를 배제한다.
  - 파라미터 저장 : 위 게인/리밋/순응/각도한계 등을 큐브 플래시(NVS)에 영구 저장해 전원
    사이클 후에도 유지한다.
  - BLE 프로토콜 대응: SetDriveState · SetTargetTorque · SetComplianceMode ·
    SetControlGains · SetMotionLimits · SetFaultThresholds · SetAngleLimits · SaveParameters.
  ※ 3단 안전: (관절)각도 소프트리밋 -> 폴트 임계 트립 -> edge central IK 단계의 해 배제.

9. 센서 모니터링
================================================================================

[서브로봇유닛]   ★혼합 반영
  - 원하는 R큐브가 모두 접속 완료되면, PC 제어 프로그램이 센서 전송 시작 명령을
    보낸다.
       · CAN 세팅 큐브 : 각 큐브가 유닛 CAN 버스를 통해 PC(USB-CAN 어댑터)에 직접
         주기적으로 센서 데이터를 전송한다(중계 없음).
       · BLE 세팅 큐브 : 각 BLE 멤버가 BLE 허브 큐브에 센서를 보내면, BLE 허브 큐브가
         자신의 데이터와 함께 모아 BLE로 PC에 전송한다(BLE 분기 취합).

[독립로봇유닛]   ★혼합 반영 / BLE 직접
  - 필요한 모든 R큐브 연결이 완료되면 edge central이 전체 큐브에 센서 전송 시작
    명령을 보낸다.
       · CAN 멤버 : 각 큐브가 CAN으로 edge central에 주기적으로 센서를 전송한다.
       · BLE 멤버 : 각 큐브가 edge central에 BLE로 직접 주기적으로 센서를 전송한다.
         (★BLE 허브 경유 아님 - edge central이 각 BLE 멤버와 직접 연결되어 있다.)

10. 안전 정지 (Fail-safe)
================================================================================

  - 로봇 동작 중 임의의 R큐브에서 가속도 센서 기반 충격 감지 또는 모터 제어기 오류가
    발생하면, 나머지 모든 R큐브도 동작을 정지한다.

  - 정지 신호 전파 경로:   ★혼합 반영
       · 서브로봇유닛
           - CAN 큐브에서 발생 : 해당 큐브가 PC(USB-CAN)에 직접 이벤트 통보 -> PC가
             그 유닛 전체(CAN 큐브 + BLE 허브 경유 BLE 큐브)에 정지 명령 전달.
           - BLE 큐브에서 발생 : 해당 큐브 -> BLE 허브 큐브 -> PC 통보 -> PC가 전체에
             정지 명령 전달.
           (다중 유닛 공정이면 PC가 필요에 따라 다른 유닛에도 정지를 내려 라인 전체를
            정지시킬 수 있다.)
       · 독립로봇유닛
           - 해당 큐브가 edge central에 (CAN이면 CAN, BLE면 BLE로 직접) 통보 ->
             edge central이 전체 큐브에 정지 전파(각 멤버의 통신방식에 맞게).

  - 멤버 큐브 자가 정지 (공통)
       멤버 큐브는 일정 시간 명령/하트비트를 받지 못하면 스스로 정지한다.
          · CAN 멤버 : PC(서브) 또는 edge central(독립)로부터 무신호 시.
          · BLE 멤버 : (서브) BLE 허브 큐브 또는 그 위의 PC, (독립) edge central 무응답 시.
       -> 상위 제어 단절·무응답 상황에서도 멤버가 무한정 동작하지 않도록 하는
          안전장치.
       ※ (서브) BLE 허브 큐브가 정지/단절되면 그에 묶인 BLE 멤버들도 무신호로 자가
         정지하게 되므로, BLE 분기 단절도 fail-safe로 수렴한다. (독립은 edge central
         직접 연결이므로 edge central 단절 시 각 BLE 멤버가 무신호로 자가 정지한다.)

================================================================================
11. ESP32 -> STM32G4 명령 전송 주기 설계
================================================================================

[제어 계층 분담 - 핵심]   ★ESP32=키프레임 생성 / STM32G4=실시간 서보
  - ESP32(메인보드)는 실시간 서보 루프를 직접 돌리지 않는다. 20~50Hz(동작 유형에 따라
    최대 100~200Hz)로 "키프레임(목표위치 + 도달시간 또는 목표속도)"만 생성해 UART로
    STM32G4-에 내려보내는 키프레임 생성기 + 감독자(supervisor) 역할이다.
  - STM32G4-(모터제어보드)는 1kHz 이상(예: 1~10kHz)의 서보 루프로 엔코더 기반 위치/
    속도/토크를 실시간 제어하며, ESP32가 내려준 키프레임 사이를 스스로 보간해 매끄러운
    모션을 만든다. ★실시간 제어는 전적으로 STM32G4-의 몫이다.
  - 즉 "키프레임을 촘촘히 보내서" 매끄럽게 만드는 것이 아니라, "STM32G4의 고속 서보
    루프 + 보간"이 매끄러움을 만든다. ESP32 주기는 낮아도(20~50Hz) 무방하다.

[ESP32 키프레임 전송 주기 (동작 유형별)]
동작 유형                ESP32 키프레임 주기   비고
점대점(PTP) 이동, 단순 회전  20~50ms (20~50Hz)   목표값+도달시간만 주고 STM32G4가 보간 연속
궤적(스카라 보간 등)        10~20ms (50~100Hz)  협조 동작은 이 대역이 현실적
고정밀·고속 협조           5~10ms (100~200Hz)  CAN에서만 권장, BLE는 부담
  ※ 위 주기는 모두 "ESP32 -> STM32G4 키프레임 갱신 주기"이며, STM32G4 내부 서보 루프 주기
     (1kHz 이상)와는 별개다. 둘을 혼동하지 않는다(12.9 [두 개의 주기를 분리한다]).

[설계 원칙]
  - ESP32가 STM32G4에게 다음 키프레임을 제때 못 보내면 => STM32G4가 마지막 목표를 유지하며
    안전 감속, 일정 시간 초과 시 정지(STM32G4 자체 무신호 자가 정지).
  - jitter 관리 : 통신 스택과 키프레임 송출을 서로 다른 코어에 고정(pinning)하고,
    키프레임 송출은 RTOS 고정 주기 타이머로 돌리기.
  - 가가속도 제한 : 목표점만 던지고 STM32G4가 사다리꼴 속도 프로파일로 보간하도록,
    가속도와 저크(jerk)에 상한을 두면 진동·오버슈트가 크게 줄어든다.
  - 클럭 드리프트 (BLE) : 주기적인 시각 재동기(예: 상위가 일정 간격으로 기준 시각
    브로드캐스트)로 누적 오차 방지.
  - ★혼합 통신 : CAN 멤버는 5~10ms 고속 협조가 가능하지만, BLE 멤버는 결정적이지
    않으므로 look-ahead 버퍼(12.9)로 지터를 흡수한다. 동일 동작 테이블이 두 분기에서
    그대로 동작하도록 전송계층 무관 웨이포인트 포맷을 쓴다(12.9).
  - ※ 독립로봇유닛에서 edge central이 BLE 멤버를 직접 다중 연결하므로, 연결 수가 늘수록
    각 BLE 링크의 connection event 스케줄링 여력이 줄어든다. R5 권장 범위에서 BLE 멤버
    수 대비 주기/지터를 실측 검증한다(12.7).

12. R큐브 소프트웨어 동작 환경
================================================================================

R큐브 한 개의 펌웨어는 ESP-IDF(FreeRTOS SMP) 기반의 네이티브 C/C++ 단일 바이너리로
빌드한다. 부팅 시 ECF에 따라 edge central 또는 멤버 큐브로 분기하고, CMF(및 edge
central이면 멤버 맵)에 따라 통신 스택을 선택한다. 역할별로 별도 펌웨어를 두지 않고
"공통 베이스 + 역할 레이어" 하나로 모든 역할을 수행한다. edge central에서 실행되는
사용자 파이썬 미션은 MicroPython을 임베디드 엔진으로 끼워 넣어 처리한다(순수
MicroPython 펌웨어가 아님).

--------------------------------------------------------------------------------
12.1 소프트웨어 스택 - ESP-IDF 네이티브
--------------------------------------------------------------------------------
  - 베이스: ESP-IDF + FreeRTOS SMP (듀얼코어).
  - 언어: 공통 베이스/실시간/역할 레이어는 C/C++. 사용자 파이썬 미션만 MicroPython.
  - 구성요소 매핑:
       · 실시간 주기     : 하드웨어 타이머(gptimer)/esp_timer + 고정주기 태스크
       · 코어 간 통신    : FreeRTOS 큐 / 링버퍼 / 스트림버퍼
       · BLE            : NimBLE 호스트
                          (멤버: peripheral / 서브의 BLE 허브: multirole /
                           ★독립의 edge central: central 다중 연결)
       · CAN            : TWAI 드라이버 (S3는 컨트롤러 1개 = 큐브당 CAN 버스 1개)
       · STM32G4- 연결  : UART 드라이버
       · 설정 플래그 저장 : 플래시 (공통 ECF·CMF·노드ID·그룹번호 / CMF=1: 종단노드ID /
                          ★edge central: N·종단노드ID·멤버 {노드ID, CMF} 맵)
       · 펌웨어 갱신     : esp_ota + 앱 롤백/안티롤백 (2-OTA 파티션)
       · 워치독         : Task WDT + 모션 태스크 자체 타임아웃
       · 센서/표시      : SPI(IMU)/I2C(거리센서), LEDC/RMT(칼라LED), LEDC(부저),
                         GPIO(종단 스위치)
  - ★혼합 통신과 스택 동시 운용:
       · 일반 멤버 큐브는 자신의 CMF에 해당하는 단일 스택만 켠다(CMF=0->NimBLE
         peripheral, CMF=1->TWAI).
       · BLE 허브 큐브(서브 전용)는 NimBLE를 multirole(peripheral+central)로 운용한다.
       · edge central(독립로봇유닛)은 저장된 멤버 맵에 따라 필요한 서버만 켠다.
         (CAN 멤버가 있으면 TWAI, BLE 멤버가 있으면 NimBLE central. 둘 다면 동시 운용.
          ESP32-S3는 BLE와 TWAI가 독립 페리페럴이므로 동시 운용 가능.)
         ★edge central의 BLE는 각 BLE 멤버에 직접 연결하는 central 다중 연결이며,
         BLE 허브를 쓰지 않는다.
       · 설정 모드는 ECF/CMF/멤버맵과 무관하게 NimBLE를 advertising-only(peripheral)로만
         켠다. (12.6 [설정 모드 분기] 참조)
  - 단일 펌웨어 원칙: 같은 바이너리가 부팅 분기로 모든 역할을 수행하므로 OTA·디버깅을
    한 펌웨어로 관리한다.

--------------------------------------------------------------------------------
12.2 코어 배치 - 제어는 공통(Core 1), 역할은 분기(Core 0)
--------------------------------------------------------------------------------
  - 모든 R큐브는 역할/통신방식과 무관하게 자기 모터 1개를 고정 주기로 제어한다.
    실시간 모션 제어는 공통이며, 역할/통신에 따라 갈리는 것은 통신·명령 생성 부분뿐.
    ※ 여기서 ESP32 Core 1의 "고정 주기"는 STM32G4로 키프레임/목표를 송출·감독하는 20~
      50Hz급 주기를 말한다. 1kHz 이상 실시간 서보 루프는 STM32G4-가 담당한다(11/12.9).
  - ESP32-S3 듀얼코어를 물리적으로 분리한다.
       · Core 0 (통신/역할) : NimBLE/TWAI 스택, 역할 레이어, 데이터테이블 시퀀서,
                              MicroPython VM. jitter가 크고 블로킹이 잦은 작업.
       · Core 1 (실시간 제어): 고정 주기 모션 루프 + 센서 수집만. 정확한 주기가 생명.
  - 두 코어 사이는 큐로만 통신한다.

  [★ 코어 배치 실무 주의 - 기본값과 충돌]
    - ESP-IDF에서 Wi-Fi/BLE 스택은 보통 Core 0, MicroPython 태스크는 기본 Core 1에서
      동작한다(MP_TASK_COREID로 변경 가능). 기본값 그대로면 MicroPython이 실시간
      모션용 Core 1을 차지한다. 따라서:
         · 모션 태스크  : xTaskCreatePinnedToCore(..., core=1) + 고우선순위. Core 1에는
                          사실상 모션+센서 태스크만 둔다.
         · MicroPython : MP_TASK_COREID = 0 으로 Core 0에 올린다.
         · 통신 우선순위: Core 0에서 NimBLE/TWAI 태스크 우선순위를 MicroPython보다 높게
                          둬, 파이썬 GC 일시정지가 통신을 굶기지 않게 한다.
    - 부동소수(float) 태스크는 ESP-IDF가 현재 코어에 자동 핀닝하므로, 모션 루프는
      처음부터 Core 1에 명시 핀닝한다.
    - ★혼합 유닛의 edge central은 Core 0에서 NimBLE(다중 connection)+TWAI를 동시에
      돌리므로 Core 0 부하가 커진다. R5 권장과 함께 Core 0 워스트케이스를 검증한다(12.7).

--------------------------------------------------------------------------------
12.3 Core 1 - 실시간 제어 (역할/통신 무관 공통)
--------------------------------------------------------------------------------
  - 하드웨어 타이머로 깨어나는 고정주기·고우선순위 태스크가 "현재 목표값"을 받아
    (키프레임 단위로) UART로 STM32G4-에 송출한다. ※ 점과 점(키프레임) 사이의 실시간
    보간과 1kHz 이상 서보 제어는 STM32G4-가 수행하며, ESP32 Core 1은 키프레임 송출과
    감독을 담당한다.
  - IMU, 거리센서, 모터 상태(STM32G4로부터 수신)를 수집한다.
  - watchdog: 목표 갱신이 일정 시간 안 오면 안전 감속 후 정지(STM32G4도 독립적으로
    무신호 시 자가 정지).
  - 핵심: 현재 목표값이 "어디서(CAN/BLE/edge central/PC/로컬) 왔는지"를 Core 1은
    알지 못한다. 이 무지(無知)가 구조를 단순하게 만든다.
  - 설정 모드에서는 Core 1이 목표를 받지 않으므로 모터는 정지 상태를 유지한다.

--------------------------------------------------------------------------------
12.4 Core 0 - 역할 레이어 (ECF로 분기, CMF/멤버맵으로 스택)
--------------------------------------------------------------------------------
  [멤버 레이어 - ECF = 0]
    - 네트워크(상위)에서 동작 명령을 받아 Core 1 목표 큐에 적재한다.
        · 서브 : CAN 멤버는 PC, BLE 멤버는 BLE 허브 경유.
        · 독립 : CAN 멤버는 edge central(CAN), BLE 멤버는 edge central(BLE 직접).
    - Core 1이 모은 센서 데이터를 주기적으로 리포팅한다.
    - 고정형이라 자기 노드ID를 이미 알고 있으므로, 연결되면 자기 노드ID 색상 LED를
      스스로 켠다(상위의 색상 명령은 확인용으로만 필요).
    - ★종단은 연결 시 받아서가 아니라, 부팅 시 플래시의 종단노드ID로 자가 결정한다
      (CMF=1이고 노드ID==종단노드ID이면 종단 ON; 12.6 4단계/13장).
    - 본질적으로 "네트워크 <-> 모션 큐"의 중계자이다.

    [BLE 허브 add-on - 서브 전용 / BLE 분기 전용]
      - (서브에서) BLE로 세팅된 큐브 중 최소 노드ID 큐브로 지정되면, 멤버 동작에 더해
        NimBLE multirole add-on을 켠다.
      - 상위 PC에는 peripheral로 붙고, 나머지 BLE 세팅 멤버에는 central로 붙어, BLE
        멤버 센서를 취합해 PC로 올리고 PC 명령을 BLE 멤버에 분배한다.
      - ★CAN 분기에는 관여하지 않는다(CAN 큐브는 PC에 직접 붙음).
      - ★독립로봇유닛에는 이 add-on이 동작하지 않는다(edge central이 BLE 멤버를 직접 연결).

  [edge central 레이어 - ECF = 1]
    - 부팅 시 저장된 멤버 맵({노드ID, CMF}, N, 종단노드ID)을 읽어, 필요한 통신 서버만
      켠다(CAN 멤버가 있으면 TWAI, BLE 멤버가 있으면 NimBLE central. 둘 다면 둘 다).
    - 미션코드 실행 엔진을 보유한다.
       (1) 데이터 테이블 -> (C 구현) 시간축 스케줄을 읽어 각 노드(자신 포함)에 목표를
           분배하는 시퀀서/플레이어. 파이썬 없이 항상 동작.
       (2) 파이썬 코드 -> Core 0의 MicroPython VM + 사용자 코드 API(예:
           cube[2].move_to(45, t=120)). 파이썬 미션이 있을 때만 기동.
    - ★혼합 분배: edge central은 멤버 맵의 각 멤버 CMF에 따라 목표/명령을 CAN(TWAI)
      또는 BLE(NimBLE central 직접 연결)로 분배한다. 미션코드/시퀀서는 "노드ID에 목표를
      분배"만 하고, 어느 전송계층으로 나갈지는 하위 송신 레이어가 맵의 CMF로 결정한다.
    - edge central도 자기 모터가 있는 멤버이므로, 자신(노드 1)에게 목표를 분배할 때는
      네트워크로 보내지 않고 로컬 목표 큐에 직접 넣는다.

  [설정 모드 레이어 - 역할 분기 이전 우선 처리]
    - ECF/CMF/멤버맵에 따른 위 멤버/edge central 레이어를 활성화하기 전에, 설정 모드
      진입 여부를 먼저 확인한다(12.6 부팅 시퀀스). 설정 모드이면 위 레이어를 모두
      띄우지 않고, NimBLE advertising-only + 재설정 명령 처리기만 동작시킨다.
    - 처리하는 명령: ECF 해제(강등)/완전 초기화, 노드ID·CMF·그룹번호·멤버 맵 재설정,
      미션코드 교체/삭제, OTA. 적용은 플래시/LittleFS 쓰기 후 재부팅으로 반영한다.

--------------------------------------------------------------------------------
12.5 MicroPython의 위치와 임베딩
--------------------------------------------------------------------------------
  - 파이썬은 edge central에서만 실행되며, "무엇을 할지"(고수준 시퀀싱) 결정만 담당.
  - MicroPython은 GC로 실행 시간이 들쭉날쭉하므로 "정확한 타이밍 실행"은 Core 1의 C
    스케줄러가 담당한다. 예) move_to(45, t=120)은 목표 등록일 뿐이며, 120ms 보간·송출은
    Core 1이 수행한다.
  - 파이썬 API는 "목표를 코어 간 큐에 적재"하는 일만 한다(SPI·타이머 직접 제어 금지).
  - 임베딩 방식:
       · MicroPython embed 포트(ports/embed)를 ESP-IDF 컴포넌트로 감싸 빌드에 포함.
       · 코드생성 결합 난점은 MicroPython 코드생성을 IDF 빌드 안에서 돌려 해소.
       · 큐브 제어 API는 frozen module로 굽고, 사용자 파이썬은 mpy-cross로 .mpy 선컴파일.
  - 메모리: PSRAM 탑재 모듈 권장 (예: ESP32-S3-WROOM-1 N16R8 = 16MB 플래시 / 8MB PSRAM).

--------------------------------------------------------------------------------
12.6 부팅 시퀀스 (app_main 기준)   ★혼합/멤버맵/설정모드 반영
--------------------------------------------------------------------------------
  1) app_main(C) 진입 -> 플래시에서 ECF·CMF·노드ID·그룹번호를 읽는다. ★CMF=1(CAN)
     큐브는 종단노드ID도, edge central(ECF=1)이면 전체 큐브 수 N과 멤버 {노드ID, CMF}
     맵도 함께 읽는다.
  2) 공통 초기화(역할 무관): Core 1 모션 태스크 핀닝 기동, STM32G4 UART, 센서, 칼라LED,
     외부확장포트 자동 탐지(I2C->UART->Analog 순, 2장), 상태 머신 초기화.
  3) 통신 스택 선택·초기화:
       · 일반 멤버 : 자신의 CMF에 따라 단일 스택.
            - CMF=0(BLE): NimBLE peripheral (컨트롤러가 플래시를 쓰므로 nvs_flash_init 선행).
            - CMF=1(CAN): TWAI (OTA/플래시 쓰기 중에도 살리려면 TWAI ISR을 IRAM에
              배치 = CONFIG_TWAI_ISR_IN_IRAM).
       · BLE 허브 큐브(서브 전용) : NimBLE multirole.
       · edge central(ECF=1) : ★저장된 멤버 맵을 보고 필요한 서버만 초기화한다.
            - 멤버에 CAN이 있으면 TWAI, BLE가 있으면 NimBLE central. 둘 다면 둘 다.
              (CAN만 -> TWAI만, BLE만 -> NimBLE만)
            - BLE는 각 BLE 멤버에 직접 연결하는 central 다중 연결로 띄운다(허브 없음).
            - ★연결 순서(conn_handle)는 노드ID와 무관하다. 각 연결을 광고의 노드ID
              (RCUBEROBOT.GG.NN)에 바인딩해 "노드ID -> conn_handle" 매핑 테이블을 둔다.
              상위는 노드ID로만 주소 지정하고, 송신 레이어가 노드ID->handle(BLE) 또는
              노드ID->메시지ID(CAN)로 변환한다. (disconnect 시 handle 무효화, 재연결 시
              광고 노드ID로 재바인딩.) (12.4 참조)
  4) 종단 GPIO 설정(13장): 종단노드ID는 서브·독립 공통으로 통신방식 세팅 저장 단계
     (7.2/7.3)에서 각 CAN 큐브 플래시에 미리 기록된 값이므로, 여기서 플래시만 읽어
     비교한다(연결/CAN 통신 불필요).
       · 일반 멤버 : CMF=1이고 노드ID==종단노드ID이면 ON. 그 외(가운데 CAN 큐브,
         또는 BLE 멤버)는 OFF.
       · edge central(노드01) : ★자기 CMF와 무관하게, 멤버 맵에 CAN 멤버가 있으면
         CAN 버스에 올라가 자기 끝을 ON. (CAN 멤버가 없으면 OFF.)
  5) ECF로 역할 레이어 결정:
       · ECF=0 -> 멤버 레이어 활성화. (서브에서 PC가 이 큐브를 BLE 허브로 지정하면
         그때 multirole add-on을 켠다. 부팅 시 자가 판단이 아니라 PC의 런타임 지정이다.)
       · ECF=1 -> edge central 레이어 활성화. 데이터테이블 엔진은 항상, MicroPython VM은
                 파이썬 미션이 있을 때 Core 0에 기동. 멤버 맵대로 노드ID 순서 연결 개시.
  -> 같은 바이너리가 부팅 분기로 모든 역할이 되므로, OTA·디버깅을 단일 펌웨어로 관리한다.

  [★ 설정 모드 분기 (12.6 보강)]
    - 위 2) 공통 초기화 후 대기모드에서 버튼을 3초 이상 길게 눌렀다 놓으면, 3)~5)의
      CMF/ECF/멤버맵 기반 스택·역할 결정을 건너뛰고 "설정 모드"로 진입한다.
    - 설정 모드는 플래시의 ECF/CMF/멤버맵 값과 무관하게 NimBLE를 advertising-only
      (peripheral)로만 띄우고(광고 이름 RCUBECONFIG.GG.NN), TWAI/edge central/멤버
      레이어는 띄우지 않으며, 모터는 중립(목표 미적재)으로 둔다. 종단 스위치도 OFF 유지.
    - PC/앱이 연결해 ECF 해제(강등)·노드ID/CMF/멤버맵 재설정·미션코드 교체/삭제·OTA를
      수행한 뒤 재부팅하면, 그때 비로소 새 설정으로 3)~5) 정상 분기를 탄다.
    - 구현 메모: 대기모드에서 버튼 down 시각을 기록하고 release 시 3초 경과 여부로
      분기. 3초 경과 순간 LED를 설정 모드 표시(흰색 0.25초 점멸)로 바꿔 사용자에게
      알린다. (5장 [설정 모드] 정합)

--------------------------------------------------------------------------------
12.7 안정성 보강 항목
--------------------------------------------------------------------------------
  - 명시적 상태 머신 : 부팅 -> 연결대기 -> 연결완료 -> 동작대기(armed) -> 실행 -> 정지
                     상태를 명시 관리하여 경계 상황을 거른다. 설정 모드는 별도 상태로
                     두어, armed/실행 상태에서는 진입/명령 수용을 막는다.
  - 메시지 시퀀스 번호 : 절대 목표+타임스탬프에 순번을 넣어, 순서가 뒤바뀐 오래된
                     목표를 멤버가 버릴 수 있게 한다.
  - edge central 과부하 감시 : ★혼합 유닛 edge central은 자기 모터 제어 + 다중 노드
                     조정 + 미션 실행 + (NimBLE 다중 connection + TWAI 동시 운용)을
                     한꺼번에 하므로, R5 권장과 함께 Core 0 워스트케이스 부하를 반드시
                     검증한다. ★특히 BLE 멤버 직접 다중 연결 수가 늘 때의 부하를 본다.
  - 코어 격리 검증 : Core 1 모션 주기 jitter를 측정해, Core 0의 BLE/CAN 폭주나 GC가
                     Core 1 주기를 밀지 않는지 확인한다.
  - CAN 무중단 : OTA·플래시 쓰기 중 TWAI ISR(IRAM)이 송수신을 유지하는지 검증한다.
  - watchdog 정합 : Core 1 무신호 자가 정지, STM32G4 독립 자가 정지, 멤버의 상위 무응답
                     자가 정지(10장)가 서로 모순 없이 동작하는지 점검한다.
  - 멤버 맵 정합 : edge central에 저장된 멤버 맵과 실제 연결된 큐브(노드ID/CMF)가
                     불일치할 때의 처리(누락 노드ID 대기/타임아웃, 예상치 못한 통신방식
                     출현 시 경고)를 정의한다. ★

--------------------------------------------------------------------------------
12.8 미션코드의 변환·전송·저장·실행 분담
--------------------------------------------------------------------------------
  미션코드(특히 사용자 파이썬)는 펌웨어에 컴파일해 넣지 않는다. 펌웨어에 들어가는 것은
  MicroPython 인터프리터(및 frozen된 큐브 API)뿐이고, 사용자 코드는 "런타임에 업로드되어
  인터프리터가 실행하는 데이터"로 다룬다.

  [역할 분담 한눈에]
    · PC(제어 프로그램/업로드 툴)  : 변환 + 전송
    · R큐브 네이티브 스택(C)        : 수신 + 검증 + 저장
    · MicroPython(edge central)    : 실행 (C가 읽어 넘겨준 코드만)

  (1) PC 측 - 변환 + 전송
      - 형식 선택:
           · 원본 .py 소스   : 변환 없이 전송. 큐브가 실행 시 컴파일. 단순(브링업용)하나
                              시작 지연·RAM·소스 노출.
           · .mpy 바이트코드 : PC에서 mpy-cross로 선컴파일 후 전송. 시작 빠르고 작고
                              소스 비노출. 제품용 권장.
      - .mpy 버전 호환(중요): .mpy 버전이 큐브 펌웨어의 MicroPython 버전과 일치해야 한다.
        큐브 MicroPython 버전을 고정하고 맞는 mpy-cross를 함께 배포한다.
      - 전송: 헤더(포맷 py/mpy, 길이, CRC32, .mpy 버전, 이름) -> 데이터 청크(offset/순번)
        -> 커밋(CRC 검증).
           · 리드 큐브가 BLE면 : 업로드용 GATT characteristic으로 청크 전송.
           · 리드 큐브가 CAN면 : PC가 리드 큐브(노드01)에 ISO-TP 멀티프레임으로 직접 전송.
        ※ 미션코드와 멤버 맵은 항상 리드 큐브(노드01)에 업로드/저장한다(독립 전환 시
          edge central이 됨).
        ※ 이미 독립로봇유닛이 된 edge central의 미션코드/멤버 맵을 교체하려면 설정 모드로
          진입해 업로드용 채널을 연다. (5장 [설정 모드])

  (2) R큐브 네이티브 스택(C) 측 - 수신 + 저장
      - 청크를 재조립하고 CRC/길이/버전을 검증한다.
      - 임시 파일에 쓴 뒤 원자적 rename으로 LittleFS 미션 파티션에 커밋한다. 메타데이터
        (멤버 맵 포함)는 플래시에 작게 둔다.
      - 상태 머신으로 armed/실행 중에는 업로드를 거부하고 연결/대기/설정 상태에서만 받는다.
      - 중요: 이 수신·저장은 리드 큐브가 아직 서브로봇유닛 멤버(ECF=0)일 때 일어난다. 즉
        코드를 "보관만" 하고 "실행은 안 한다". 데이터테이블 미션도 같은 저장 메커니즘을
        공유한다(엔진만 다름).

  (3) MicroPython(edge central) 측 - 실행
      - ECF=1로 부팅한 뒤에만 실행된다. C가 LittleFS에서 미션 바이트를 읽어 Core 0의
        MicroPython 전용 태스크에 넘긴다.
           · .py 소스 : mp_embed_exec_str(소스버퍼)
           · .mpy     : persistent code load + raw-code 로더로 실행
      - 큐브 API(move_to 등)는 목표를 코어 간 큐에 적재만 하고, 실제 타이밍은 Core 1이
        수행한다. 정지는 태스크 리셋/리부팅 + 워치독으로 처리한다.

--------------------------------------------------------------------------------
12.9 ESP32 -> STM32G4 감독 루프와 웨이포인트 스트리밍
--------------------------------------------------------------------------------
  각 R큐브에서 ESP32는 STM32G4-에 UART로 모터 목표값을 내려보내고, STM32G4-가 실제
  서보 제어를 전담한다.

  [두 개의 주기를 분리한다]
    - 서보 루프 주기(STM32G4 내부) : 엔코더 기반 위치/속도/토크 제어 루프. ★1kHz 이상
      (예: 1~10kHz)으로 STM32G4-가 실시간 수행한다. 모터의 매끄러움은 여기서 결정된다.
    - 웨이포인트(목표값) 갱신 주기(ESP32 -> STM32G4) : 다음 목표점을 내려보내는 주기.
      11장 표의 "ESP32 키프레임 주기"(20~50Hz급)가 이쪽이다.
    - ★두 주기를 혼동하지 않는다: ESP32는 20~50Hz로 키프레임만, STM32G4는 1kHz 이상으로
      실시간 서보·보간. 웨이포인트를 촘촘히 보내서 매끄럽게 만드는 것이 아니라, STM32G4의
      고속 서보 루프와 보간이 매끄러움을 만든다.

  [웨이포인트 갱신 주기 - 표준 50ms + STM32G4 보간]
    - 동작 테이블의 단위동작 간 표준 간격은 50ms(20Hz). ESP32는 "목표 위치 + 도달시간
      (또는 목표속도)"만 키프레임으로 내려보내고, 점과 점 사이 프로파일은 STM32G4가 생성.
    - 고속·고정밀 협조가 필요하면 10~20ms로 좁히되, BLE에서는 부담이 크므로 CAN에서만
      권장한다.

  [ESP32의 감독자(supervisor) 역할]
    - ESP32는 STM32G4와 매 주기 양방향으로 주고받아 "STM32G4가 제대로 따라오는지" 감시한다.
         · 추종오차(following error) : 임계 초과 시 폴트.
         · 모터 전류/토크 : 충돌·잼·과부하 감지. 집게 큐브는 "물체 잡힘/놓침"까지 판단.
         · 명령수행현황·오류현황·온도, STM32G4 하트비트 확인.
    - 상호 watchdog: STM32G4는 무신호 시 마지막 목표 유지 후 안전 감속·정지. ESP32는 STM32G4
      하트비트 끊기면 폴트 -> 멤버면 자가 정지·상위 통보, edge central/PC면 정지 전파.

  [동작 시퀀스 진행 게이팅 - 시간 기반 + 확인 혼합]
    - 평상시 : 시간 기반(50ms)으로 흘리되 추종오차를 감시. 한계 초과 시 폴트/일시정지.
    - 결정적 지점(집기/놓기) : in-position 확인(handshake) 후에만 그리퍼를 여닫는다.

  [BLE 전송 시 지터 대응 - look-ahead 버퍼]   ★혼합에서 특히 중요
    - CAN은 50ms가 거의 그대로지만 BLE는 결정적이지 않다(connection event/재전송으로
      수십 ms 지터).
    - 따라서 BLE 멤버 큐브는 키프레임을 2~3개(약 100~150ms 분량) 미리 큐잉해 지터를
      버퍼가 흡수하게 한다.
    - connection interval은 50ms보다 충분히 짧게(예: 25ms 이하) 잡는다. ★독립로봇유닛에서
      edge central이 다수 BLE 멤버를 직접 연결할 때, central 측 connection event 스케줄
      여력을 실측 검증한다(12.7).
    - 키프레임에 도달시각(타임스탬프)과 가능하면 목표속도를 실어, 공통 시각 기준으로
      다축 동기 시작을 맞춘다.
    - 링크 단절(supervision timeout) 시 STM32G4 자가 정지 + 멤버 자가 정지로 fail-safe.

  [버퍼 실행 모델 - 즉시 실행 vs 적재 후 일제 실행]   ★다축 동기의 핵심
    - 모션 명령은 두 가지 실행 모드를 갖는다.
        · 즉시(Immediate) : 받는 즉시 실행한다(단일 축 단순 이동 등).
        · 적재(Buffered)  : 곧바로 실행하지 않고 큐브의 모션 버퍼에 쌓아 둔다. 이후 별도의
                           "실행 트리거"를 받아야 비로소 출발한다.
    - 다축 동기 출발은 이 적재 모드로 구현한다: edge central이 각 축(큐브)에 궤적을 미리
      Buffered로 적재한 뒤, 공통 시각 T0를 실은 "실행 트리거"를 브로드캐스트하면 전 축이 T0에
      일제히 출발한다. (BLE 지터는 look-ahead 버퍼가, 시작 시점은 T0가 맞춘다.)
    - 트리거는 실행 시작(Run)뿐 아니라 실행 중 취소(Cancel)·미실행 버퍼 폐기(Flush)도 포함한다.
      빈 버퍼를 Run하면 거부된다.
    - BLE 프로토콜 대응: 모션 명령의 Mode{Immediate/Buffered} + ExecuteBuffer(Run/Cancel/Flush
      + StartTime=T0). 기준 시각 배포는 TimeSync.

  [전송계층 무관 웨이포인트 포맷]   ★혼합 운용의 핵심
    - 키프레임을 "도달시각 + 목표위치 + 목표속도 + 순번"으로 정의하고 멤버 큐브 측 큐잉을
      표준화하면, 같은 동작 테이블이 CAN/BLE 양쪽(혼합 유닛 포함)에서 그대로 동작한다.
    - CAN에서는 여유 있게 흐르고 BLE에서는 버퍼가 지터를 흡수하므로, 통신 모드별 코드
      분기를 최소화한다.

================================================================================
13. CAN 종단저항(120Ω) 관리
================================================================================

CAN 버스는 양쪽 물리적 끝이 종단되지 않으면 신호가 반사되어 데이터가 깨진다. 따라서
버스 양 끝에 120Ω 종단저항을 하나씩, 총 2개만 두어야 한다(두 개 병렬이라 송신 큐브가
보는 값은 60Ω). 종단이 없으면 반사로 불안정해지고, 3개 이상이면 합성 저항이 너무 낮아져
통신이 깨진다.

★혼합 통신에서는 "CAN으로 세팅된 큐브들 + 상위 제어자(PC USB-CAN 또는 edge central)"만
이 하나의 CAN 버스를 이룬다. BLE 큐브는 이 버스에 없다. 따라서 종단은 CAN 분기에 한해
관리하며, "CAN 큐브들을 노드ID 순으로 데이지체인으로 배선한다"는 규칙(아래 [CAN 배선 순서])
위에서 다음과 같이 양 끝을 닫는다.

--------------------------------------------------------------------------------
[CAN 배선(케이블 연결) 순서 - 종단 큐브를 물리적 양 끝에]   ★조립 필수 규칙
--------------------------------------------------------------------------------
  종단저항은 CAN 버스의 "물리적 양 끝" 큐브 2개에서만 켜진다(13.3). 따라서 어느 큐브가
  물리적 끝에 오는지는 케이블 연결 순서가 결정하며, 이 순서를 지켜야 자가 종단(13.4)이
  정확히 양 끝에 걸린다. 순서가 어긋나면 종단이 가운데에 켜지거나 한쪽 끝이 열려 CAN 통신이
  통째로 실패한다(눈에 잘 안 보이는 고장이라 주의).

  [규칙]
    1) CAN으로 세팅된 큐브들만 하나의 CAN 버스를 이룬다(BLE 큐브는 이 버스에 없다). 이
       CAN 큐브들을 노드ID 오름차순으로 한 줄(데이지체인)로 CAN 케이블 연결한다.
    2) 종단이 켜지는 두 큐브가 그 줄의 양 끝에 오도록 배치한다.
         · 독립로봇유닛 : 한쪽 끝 = edge central(노드01), 반대쪽 끝 = 최대 CAN 노드ID 큐브
                          (= 종단노드ID 큐브). 양 끝이 모두 큐브다.
         · 서브로봇유닛 : 한쪽 끝 = PC USB-CAN 어댑터(내장 종단 ON), 반대쪽 끝 = 최대 CAN
                          노드ID 큐브. 즉 큐브 줄의 바깥쪽 끝에 어댑터가 붙는다.
    3) 그 사이(가운데)의 CAN 큐브들은 종단 OFF(부팅 시 자가 판단으로 자동 OFF).
    4) BLE 큐브는 이 CAN 줄에 끼우지 않는다(별도 BLE 연결).

  [예: R4 독립로봇유닛, 노드01·02·04 = CAN, 노드03 = BLE]
    - CAN 버스 = 노드01 - 노드02 - 노드04 (BLE인 노드03은 CAN 줄에서 빠짐).
    - 종단 ON = 노드01(edge central, 한쪽 끝) + 노드04(최대 CAN 노드ID, 반대쪽 끝).
    - 노드02 = 가운데 = 종단 OFF.
    ※ 노드ID가 연속(01,02,04로 03이 빠짐)이 아니어도, CAN 큐브만 골라 노드ID 오름차순으로
      이으면 된다. 최대 CAN 노드ID(여기선 04)를 바깥 끝에 둔다.

  ※ 혼합 구성에서는 노드ID가 1..N 연속이라도 그중 일부만 CAN이므로, "CAN 큐브들만의 물리적
    끝"이 전체 노드ID 순서와 다를 수 있다. 반드시 위 규칙대로 CAN 큐브만 골라 노드ID 순으로
    잇고 최대 CAN 노드ID를 바깥 끝에 둔다. (조립 가이드 / PC 통신방식 세팅 화면에 배선도로
    안내한다.)
  ※ 이 배선 순서 가정에서 자유로워지려면 하드웨어 이웃-감지 자동 종단을 도입한다
    (부록 [C], 양산 전 검토).

--------------------------------------------------------------------------------
13.1 하드웨어
--------------------------------------------------------------------------------
  - 모든 R큐브 메인보드에 120Ω + 소프트웨어 스위치를 둔다. ESP32 GPIO로 제어.
       · 스위치 OFF : 120Ω 분리 (가운데 큐브, 기본).
       · 스위치 ON  : 120Ω이 CAN_H-CAN_L 사이에 연결 (CAN 버스 끝 큐브).
  - ※ 설정 모드에서는 항상 종단 OFF로 유지한다(설정 모드는 BLE만 사용).

--------------------------------------------------------------------------------
13.2 적용 조건 (언제 종단이 필요한가)
--------------------------------------------------------------------------------
  - 종단은 그 큐브가 CMF=1(CAN)이고, 유닛에 CAN 분기가 실제로 존재할 때만 의미가 있다.
       · 서브로봇유닛에 CAN 세팅 큐브가 있는 경우 (PC USB-CAN 어댑터가 한쪽 끝)
       · 독립로봇유닛에 CAN 세팅 큐브가 있는 경우 (edge central이 한쪽 끝)
  - 순수 BLE 유닛(또는 유닛 내 BLE 큐브)은 종단 불필요 -> 종단 스위치 OFF.
  - ★종단의 트리거는 "ECF=1" 자체가 아니라 "그 큐브가 CAN 버스에 있고 버스 끝에
    있는가"이다. 일반 멤버는 CMF=1일 때 CAN 버스에 있고, edge central(노드01)은 자기
    CMF와 무관하게 멤버에 CAN이 있으면 컨트롤러로서 CAN 버스에 올라간다. 버스 양 끝이
    모두 큐브인지(독립) 한쪽이 PC 어댑터인지(서브)는 PC가 버스에 올라와 있는가로 갈린다.

--------------------------------------------------------------------------------
13.3 종단 스위치 ON 규칙   ★혼합 반영
--------------------------------------------------------------------------------
  핵심 정의:
    - 종단노드ID = 그 유닛에서 CAN으로 세팅된 큐브 중 "최대 노드ID". (CAN 버스에서
      상위 제어자로부터 가장 먼 끝에 놓이는 큐브) edge central은 멤버 맵에서 이 값을
      산출한다.
    - 상위 제어자 = 서브: PC USB-CAN 어댑터 / 독립: edge central(노드01).

  (1) 독립로봇유닛 (CAN 분기, PC 없음)
        - edge central(노드 01)        : 멤버에 CAN이 있으면 자기 CMF와 무관하게 CAN
                                         버스에 올라가므로 종단 ON.
        - 종단노드ID 큐브(최대 CAN ID) : 종단 ON.
        - 그 사이의 CAN 큐브들          : 종단 OFF.
        - BLE 큐브                      : 버스에 없음 -> OFF.
        => 총 2개. PC가 없으므로 CAN 버스 양 끝이 모두 큐브.
        ※ 노드 01(edge central)이 CAN 버스의 한쪽 끝(상위 제어자 측)에 오도록 배선한다.

  (2) 서브로봇유닛 (CAN 분기, PC의 USB-CAN 어댑터가 버스에 올라옴)
        - PC USB-CAN 어댑터    : 버스 한쪽 끝 종단(어댑터 내장 종단 ON).
        - 종단노드ID 큐브       : 종단 ON.
        - 나머지 CAN 큐브       : 종단 OFF.
        - BLE 큐브              : 버스에 없음 -> OFF.
        => PC 어댑터 + 종단노드ID 큐브 = 총 2개.
        ※ CAN 서브에는 중계 큐브가 없다(취합 주체 = PC). PC 어댑터가 이미 한쪽 끝을
          종단하므로, 그쪽 끝에 가까운 CAN 큐브가 추가로 켜지면 종단이 3개가 되어
          통신이 깨진다.

--------------------------------------------------------------------------------
13.4 종단노드ID의 사전 기록과 종단 스위치를 켜는 방식 (부팅 시 자가 종단)   ★방법1
--------------------------------------------------------------------------------
  핵심: 종단노드ID를 "연결 시 런타임으로 전달"하지 않는다. 통신방식 세팅을 저장하는
  단계에서 각 CAN 큐브 플래시에 미리 기록해 두고, 부팅 시 큐브가 스스로 비교해 켠다. 이렇게
  하면 CAN 통신(핸드셰이크) 이전에 종단이 정해지므로, 종단 전 버스에서 값을 주고받아야
  하는 부트스트랩 문제가 없다.

  [표준 방식 - 세팅 저장 시 종단노드ID 사전 기록 + 부팅 시 자가 종단]
    (1) 사전 기록 (통신방식 세팅 저장 단계, 7.2 서브 / 7.3 독립)
        - PC는 전체 큐브의 CAN/BLE 선택 결과에서 종단노드ID(= CAN 세팅 큐브 중 최대
          노드ID)를 산출한다.
        - PC는 각 CAN 큐브(CMF=1)의 플래시에 노드ID/CMF와 함께 이 종단노드ID를 기록한다.
          (독립로봇유닛이면 edge central도 멤버 맵에 이 값을 갖는다.)
    (2) 부팅 시 자가 종단 (reset/전원 ON 직후, 12.6 4단계)
        - CMF=1인 각 CAN 큐브는 플래시의 종단노드ID와 자기 노드ID를 비교해, 같으면 종단
          스위치를 켠다. CAN 통신 없이 로컬에서 결정한다.
        - 반대쪽 끝 종단:
             · 독립로봇유닛 : edge central(노드 01)은 자기 CMF와 무관하게 멤버 맵에 CAN
                          멤버가 있으면 부팅 시 자기 종단 ON (CAN 버스 상위 끝).
             · CAN 서브 : PC USB-CAN 어댑터가 담당(어댑터 내장 종단 ON). 노드 01 등
                          다른 큐브는 OFF — 켜면 종단이 3개가 되어 통신이 깨진다.
    => 부팅 시점에 CAN 버스 양 끝(종단노드ID 큐브 + (edge central 또는 PC 어댑터))에만
       종단 2개가 켜져, 첫 CAN 트래픽부터 정상 종단이다.

  ※ 이 방식은 "CAN 큐브가 노드ID 순으로 데이지체인되어 종단노드ID 큐브가 물리적 끝에
     온다"는 배선 가정에 의존한다. 배선 가정에서 자유로운 하드웨어 이웃-감지 자동 종단은
     부록 [C]의 장기 옵션이다.

  ※ BLE 세팅 큐브는 이 절차와 무관하다(항상 종단 OFF).

부록. 결정 사항 및 추후 상세 확정 항목

  [B] 모드 전환 시 reset/shutdown 전파 방식   ★[결정] 명시 명령으로 통일
      - 결정: 모드 전환(reset/shutdown)은 항상 "명시적 명령(정식 OpCode)"으로 전달한다.
        "BLE 링크 끊김"은 정상 절차 신호로 쓰지 않는다.
      - 역할 분리: 정상 절차 = 명시 명령(reset/shutdown/E-stop 등), 비정상 = 링크 끊김 ->
        오직 fail-safe(무신호 자가 정지, 10장)의 트리거로만 쓴다. 이렇게 나누면 "어떤
        큐브는 재부팅, 어떤 큐브는 멈춤"식 엇갈림이 사라진다.
      - 남은 상세: 각 명령의 ACK/타임아웃, 전(全)큐브 브로드캐스트 시 누락 재전송 정책은
        프로토콜 상세에서 확정.

  [C] 종단 큐브의 물리적 위치   ★[결정] 단기=강제 배선 규칙 / 중장기=이웃-감지 자동 종단
      - 배경: 13장 종단 규칙은 "CAN 큐브들이 노드ID 순으로 데이지체인되어 상위 제어자
        (edge central/PC 어댑터) 측과 최대 CAN 노드ID 큐브가 양 물리적 끝에 온다"는 배선
        가정에 의존한다. 혼합 구성에서는 일부만 CAN이라 이 가정이 깨지기 쉽고, 깨지면
        종단이 엉뚱한 곳에 켜져 CAN 통신이 통째로 실패한다(눈에 안 보이는 실패).
      - [결정-단기] 조립 가이드에 강제 배선 규칙을 명문화한다: "CAN 큐브는 반드시 노드ID
        오름차순으로 한 줄 데이지체인으로 잇고, 상위 제어자(PC USB-CAN 어댑터 / 노드01)
        측 끝과 최대 CAN 노드ID 큐브를 양 끝에 둔다." PC 통신방식 세팅 화면에 배선도로
        안내한다. (현행 방법1(13.4: 세팅 저장 시 종단노드ID 사전 기록 -> 부팅 자가 종단)은
        이 배선 규칙 위에서 유효.)
      - [결정-중장기, 양산 전 도입 권장] 각 큐브가 자기 CAN 링크 커넥터에 옆 큐브 유무를
        감지(링크면 존재 핀)해, "한쪽에 이웃 없음 = 내가 버스 끝 = 종단 ON"으로 자동
        판단하는 하드웨어를 도입한다. 배선 순서 가정 자체를 제거해 사용자 실수에 강하다
        (산업용 신뢰성 확보). 도입 시 방법1의 종단노드ID 사전 기록은 불필요해진다.
      - 남은 상세: 이웃-감지 핀 회로 방식, CAN 버스/스터브 길이 권장값, PC USB-CAN 어댑터
        종단 ON/OFF 설정 방법.

  [D] 다중 유닛 공정의 PC측 구성
      - PC 1대에 붙일 USB-CAN 채널 수 상한, 다채널 USB-CAN 장치 선정 기준, "채널 <-> 유닛"
        매핑 관리 방식.
      - ★유닛마다 CAN/BLE 혼합인 경우, PC가 한 유닛에 대해 USB-CAN(직접) + BLE(허브 경유)
        두 경로를 동시에 다루는 동시성/스케줄링 부하 검증.
      - 라인 전체 정지(E-stop) 시 PC가 여러 유닛의 CAN/BLE 분기 모두에 정지를 내리는 조율
        로직과 응답 보장(누락/지연) 방식.

  [F] 설정 모드(Config Mode) 보안/인증   ★[반영] 기존 PEM 기반 펌웨어 서명 인프라 활용
      - 전제(반영): 현재 펌웨어 빌드에 PEM(서명 키/인증서)을 사용하므로, 이 키 인프라를
        설정 모드 보안에 그대로 확장한다. 3계층 접근 제어를 둔다.
          · 1차(물리) : 버튼 3초 롱프레스 = 물리 접근 필요(현행 유지).
          · 2차(이미지 서명 검증) : OTA는 제조사 개인키(PEM)로 서명된 이미지만 수용하고,
            큐브는 내장된 공개키(PEM)로 검증한다. 서명 없음/불일치 이미지는 거부한다
            (Secure Boot / Signed OTA). 이로써 임의 앱의 펌웨어 교체를 원천 차단.
          · 3차(명령 인증) : 초기화·ECF 해제·OTA 등 "파괴적 명령"은 같은 PEM 키쌍 기반
            챌린지-응답으로 인증한다(큐브가 난수 챌린지 발급 -> 제조사 앱이 개인키로 서명
            -> 큐브가 공개키로 검증). 단순 조회는 인증 없이 허용해 편의를 유지한다.
      - 보조: 그룹번호 일치 확인(옆 유닛 오조작 방지) + 설정 모드 자동 타임아웃(무연결
        일정 시간 후 자동 종료).
      - 롱프레스 임계시간(기본 3초), 설정 모드 표시(LED 흰색 0.25초 점멸)·진입 멜로디의
        최종 값은 상세 설계에서 확정.
      - 남은 상세: 공개키의 큐브 내 저장 위치(eFuse/보안 파티션), 키 롤오버 정책, 챌린지
        난수·세션 수명.
